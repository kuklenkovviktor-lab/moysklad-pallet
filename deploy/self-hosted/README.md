# ONIX 1.0 — собственный сервер + PostgreSQL + собственный домен

**Статус:** конфигурация для нового, отдельного VPS. Пока нет созданного VPS и проверенного домена, никакой перенос не произведён. **Текущий Render не трогать до сквозного испытания и подтверждённого бэкапа.**

## Архитектура

```
Android / iPhone / ПК склада без VPN
  |
  | HTTPS https://ваш-домен (443)
  v
Ubuntu 24.04 VPS (Москва, под управлением владельца)
  Caddy -> ONIX Flask/Gunicorn -> PostgreSQL 16 (только Docker internal)
                          \-----> MoySklad / Wildberries APIs (исходящие HTTPS)
  |
  +--> локальный pg_dump и обязательная ЗАШИФРОВАННАЯ внешняя копия
```

Нет прокси к Render, нет привязки к `onrender.com`, нет опубликованного PostgreSQL порта. Сервер, домен и резервные копии оформляются на личный аккаунт владельца ONIX.

Предлагаемая стартовая мощность: **2 vCPU / 4 ГБ RAM / 50 ГБ NVMe / публичный IPv4**. Это стартовая оценка, не результат нагрузочного теста. Для PyMuPDF и 4 комплектов сотрудников + 3 менеджеров может понадобиться 4 vCPU / 8 ГБ, проверять по P95 и расходу памяти. Время работы без сна 24/7. Перед оплатой проверь стоимость выбранной конфигурации с IPv4 и автоматическими снапшотами.

## Шаг 0. Право собственности и покупка

1. Создать личный аккаунт у провайдера VPS, **на свои контактные данные**; предпочтителен VPS в Москве, например Timeweb Cloud, Ubuntu 24.04 LTS. На этапе заказа указать публичный IPv4 и SSH public key. **Никогда не присылай в чат SSH private key или пароль root.**
2. Зарегистрировать личный домен (например, `onix-что-то.ru`, но только после проверки свободного имени в регистраторе). С 01.09.2026 в зоне `.ru`/ `.рф` требуется идентификация через ЕСИА. Настроить DNS A-запись на публичный IPv4 VPS. Не указывать вымышленный домен из этого файла.
3. На телефоне **в складском Wi-Fi с выключенным VPN** проверить TCP 443 до нового VPS и доступность домена по HTTPS. Если новый адрес тоже ограничен провайдером, STOP: оплату/развёртывание не продолжать до анализа сети.
4. Сохранить подтверждение оплаты и доступы под личным аккаунтом, включить 2FA, регулярные снапшоты и мониторинг. Расходы (VPS, домен, внешнее резервное хранилище, IPv4) оплачиваются отдельно.

## Шаг 1. Защитить исходную PostgreSQL на Render

Не перепутать: `storage_backup.py` резервирует **только SQLite** и НЕ резервирует действующую PostgreSQL.

- Render Postgres 16 `onix-wms-postgres` (Frankfurt) имеет срок бесплатной эксплуатации до **11.11.2026 09:50:59 UTC**. Переносить после этой даты опасно.
- Сначала сделать **полный PostgreSQL custom-format backup** через `pg_dump -Fc`, сохранить отдельно от VPS и протестировать пробное восстановление. Render Free не предоставляет автоматические управляемые бэкапы.
- Для выгрузки извне использовать в Render Dashboard внешний URL PostgreSQL и временно разрешить **только исходящий публичный IP /32 устройства, с которого запускается pg_dump**. Все внешние соединения Render Postgres используют TLS. Никаких правил `0.0.0.0/0`. После выгрузки удалить временное правило IP.
- Используй PostgreSQL 16 client tools для дампа PostgreSQL 16. При ручном подключении следи за `sslmode=require`. Не публикуй URL БД, пароли и дамп в чате, GitHub или скриншотах.
- Зафиксировать в двух базах счётчики строк ключевых таблиц (см. ниже). Тестовый восстановленный дамп — обязательная предпосылка перед cutover.

## Шаг 2. Подготовка Ubuntu VPS

На новом VPS настроить SSH-ключи, отключить вход по паролю после проверки доступа по ключу, ограничить SSH своим IP; публично открыть только TCP 80/443; не открывать PostgreSQL 5432 и Gunicorn 8000. Обновить ОС, установить Docker Engine + Compose plugin из официального репозитория.

Склонировать `kuklenkovviktor-lab/moysklad-pallet` **на утверждённом commit после проверки PR**, например в `/opt/onix` (репозиторий приватный, копируй доступ безопасно).

```sh
cd /opt/onix/deploy/self-hosted
cp .env.example .env
# В .env заменить ONIX_DOMAIN=wms.example.ru на реально зарегистрированный домен
umask 077
mkdir -p secrets backups
# Новый пароль отдельного PostgreSQL на VPS:
openssl rand -hex 32 > secrets/postgres_password
```

Создать остальные файлы в `secrets/` **вручную, не публиковать содержимое**:

| Файл | Какое значение |
|---|---|
| `flask_secret` | Точное значение `SECRET_KEY` из текущего Render |
| `badge_secret` | Точное значение `WMS_BADGE_SECRET` из Render (иначе QR-бейджи перестанут работать) |
| `terminal_secret` | Точное значение `WMS_TERMINAL_SECRET` из Render (иначе QR выхода изменятся) |
| `manager_password` | Текущее `MANAGER_WEB_PASSWORD` |
| `moysklad_token` | Текущее `MOYSKLAD_TOKEN` |
| `wb_api_token` | Текущее `WB_API_TOKEN`, если не используется — пустой файл |
| `postgres_password` | Новый пароль, созданный выше |

`chmod 700 secrets`; `chmod 644 secrets/*`; `chmod 600 .env`. В Compose nonroot-контейнер читает только явно примонтированные ему secrets; каталог secrets на хосте должен принадлежать администратору и быть закрыт правами 0700. В этой конфигурации Docker Compose file-backed secrets требуют доступных на чтение файлов. Не делать каталог общедоступным. Не вводить секреты в GitHub, публичные issues, скриншоты и чаты. При необходимости переносить их в SSH/SCP или защищённом менеджере секретов. **Не менять WMS_BADGE_SECRET и WMS_TERMINAL_SECRET при переезде.**

Также скопировать из текущего Render `WB_STRICT_MATCHING` и `SUPERVISOR_QR_PERIOD` в локальную `.env`, если они отличаются от примеров. Другие специальные env, используемые текущим ONIX, нужно сверить перед cutover.

## Шаг 3. Поднять ТОЛЬКО пустую PostgreSQL

```sh
cd /opt/onix/deploy/self-hosted
docker compose config --quiet
docker compose up -d db
docker compose ps
```

Пока **не запускать** `web` и `caddy`. Действующий источник — Render — продолжает обслуживать склад.

После пробного полного `pg_dump -Fc` перенести дамп на новый сервер по SCP в `deploy/self-hosted/backups/onix-initial.dump`. Проверить список архивных объектов:

```sh
docker compose exec -T db pg_restore --list < backups/onix-initial.dump | head
```

Для восстановления в **новую, ещё не использованную БД**:

```sh
docker compose exec -T db sh -c 'PGPASSWORD="$(cat /run/secrets/postgres_password)" pg_restore -h 127.0.0.1 -U onix -d onix --no-owner --no-acl --exit-on-error' < backups/onix-initial.dump
```

**Важно:** это только dry-run проверки данных. Не переносить рабочие операции на эту копию, пока не проведён финальный перенос после остановки записей на Render.

## Шаг 4. Проверка полноты базы и тестового запуска

Сравнить source (Render) и destination (новый VPS): количество строк и содержимое ключевых сущностей. Минимальный список:

- `employees`, `shifts`, `scans`, `activities`
- `operation_events`, `external_pallets`
- `wb_orders`, `replenishment_tasks`, `replenishment_locations`
- `partner_pallets`, `receiving_operations` **если таблицы присутствуют**; точный список дополнительных таблиц получить из `pg_dump`.

Можно использовать `SELECT COUNT(*)` или снимки схемы; несовпадение означает STOP. Проверить QR-бейдж сотрудника, менеджерский пароль, роли партнёра, приёмку, пополнение, карту, WB/Ozon/Яндекс и историю без записи в действующую БД.

```sh
# Только после восстановления и валидации БД:
docker compose up -d --build web caddy
docker compose ps
docker compose logs --tail=80 web
```

Проверить `https://<реальный-домен>/login` и `/api/health`. Первая загрузка должна проходить на складском Wi-Fi **без VPN**; HTTPS-сертификат валиден. Если DNS/порт 80 недоступны, Caddy не сможет автоматически выдать сертификат.

## Шаг 5. Финальный перенос (контролируемое окно)

1. Согласовать короткое окно остановки: **всем сотрудникам прекратить сборку/приёмку/пополнение и не открывать обе системы параллельно**.
2. Остановить все источники записи в Render (включая автоматические фоновые процессы, если они пишут в БД); проверить неподтверждённые операции приёмки и внешнего МойСклад. Зафиксировать время и состояние источника.
3. Сделать **НОВЫЙ финальный pg_dump** с Render, сравнить счётчики и контрольные сведения. Это не тот же файл, что первый тестовый дамп.
4. На чистой целевой БД **без пользователей и операций после пробного restore** восстановить финальный дамп (проще удалить и заново создать отдельный тестовый volume, только после проверки пути и выгрузки). Никогда не восстанавливать прямо поверх уже работающей ONIX с текущими операциями.
5. Запустить `web` + `caddy` и проверить QR-бейджи, панели, права доступа и основные API; после разрешения Go начинается работа только через новый домен.
6. Render оставить отключённым для записей или в режиме обслуживания, чтобы никто случайно не создал две расходящиеся базы. На новом домене браузеры получат отдельные cookie: сотрудники войдут заново.
7. Rollback до начала реальных операций можно сделать на Render; **после первых реальных операций на новой БД откат не допускается без сверки и обратного переноса этих записей**.

## Шаг 6. Бэкапы и эксплуатация

Скрипт `backup.sh` создаёт local custom-format дамп PostgreSQL на VPS. Проверка формата дампа встроена, но **не заменяет проверку восстановления**. Локальный дамп вместе с сервером погибнет при потере диска: нужна автоматическая внешняя зашифрованная копия (Google Drive / объектное хранилище) и регулярные тесты восстановления.

Нужно настроить журнал ошибок, мониторинг свободного места/CPU/RAM/latency P95, предупреждения об истечении SSL и домена, обновление ОС/контейнеров и контроль резервных копий. Включить снапшоты у провайдера. Проверить одновременную работу минимум 4 сотрудников + 3 менеджеров на реальных телефонах и складском Wi-Fi.

**Отдельный P0:** баг #44 с одновременными сессиями на двух телефонах не исчезнет от переезда. До промышленного запуска нужно завершить серверную ревокацию сессий, иначе выход в одном телефоне по-прежнему не инвалидирует другой.

## Что нельзя считать завершённым после этого PR

- VPS и домен **не приобретены**, IP и DNS ещё неизвестны.
- Нет проверенного доступа именно со склада без VPN.
- Нет полного экспортированного и восстановленного дампа боевой БД.
- Нет внешнего проверенного PG backup и нагрузочного UAT.
- Новая среда **не запущена** и не может считаться production-ready.
