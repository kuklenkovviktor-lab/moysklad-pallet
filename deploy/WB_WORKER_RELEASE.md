# WB worker: проверка и ручной выпуск

## Подтверждённые причины (25.11.2026)

- Read-only `docker inspect` HOSTKEY: `grit-wb-fbs-worker` работает на
  `c0ea8ae489b18d008a6334aebf087e38a4cc2c33`, unhealthy, проверка
  `python deploy/healthcheck.py`. Этот файл требует веб-сервер на 8000;
  отдельный worker его не запускает. App `3935c9ef1753f1ea599f2ed2626e0e68bfa20699` healthy.
- Быстрый status-sync исключал `local_status=complete`, даже при WB `confirm`.
  Это объясняет механизм устаревания собранной части текущей очереди.
  Нельзя по этому факту утверждать, что все конкретные заказы уже отгружены WB.
- Дневная история читала `wb_fbs_status_tracking`, а worker v1.1 пишет
  первое подтверждение в `wb_fbs_picking_queue.accepted_at`.
- Причина старых `HTTPError` НЕ установлена: прежние сообщения не содержат
  HTTP-кода. Версия образа, неверный токен и rate limit — не доказанные диагнозы.
  Новая диагностика даст endpoint, HTTP-код, время, попытку и хеш request ID.
  Тело, токен, произвольные заголовки и текст исключений не журналируются.

## Поведение кандидата

- `wb_worker_health.py`: локальный атомарный файл прогресса, PID,
  успехи/ошибки задач; без запросов к WB, PostgreSQL и HTTP-серверу.
  Пауза прогресса >300 секунд, задача >1800 секунд или отсутствие успешных
  new/status >900 секунд — unhealthy. Короткий сбой — degraded; запуск — starting.
  Docker healthy при starting/degraded означает живой процесс в пределах окна,
  а не доказательство актуальности каталога. Для выпуска требовать именно `ok`.
  Docker сам не перезапускает контейнер лишь из-за unhealthy.
- `deploy/worker.Dockerfile` наследует проверенный app-образ и **заменяет**
  web-healthcheck; стандартный Dockerfile приложения не изменён.
- HTTP: до 4 попыток на вызов, backoff; 401/403 без повтора и cooldown 300с.
  Retry-After поддерживает секунды/HTTP-date. Длинная пауза переносится на
  следующие циклы, а не обрезается с преждевременным повтором.
- Все текущие confirm обновляются независимо от local_status; unknown после
  неполного ответа для допущенного заказа повторно проверяется. Status-запросы
  по 1000, пауза между пакетами 350мс; 4054 заказа = 5 запросов, не 4054.
  Авторитетные статусы сохраняются одной транзакцией до получения стикеров.
- PR190: состав текущего confirm, остаток и факт сканов сохранены. Актуальность
  показана по самому старому confirm, а не по одному свежему заказу.
- Поступления v1.1 считаются по accepted_at в московских сутках; неизвестные
  даты отдельно. Никаких подстановок created_at/сегодня. Новая аддитивная таблица
  `wb_fbs_delivery_observations` фиксирует только наблюдаемый confirm→complete,
  однократно на аккаунт/заказ. Исторические переходы не восстанавливаются.
  Нулевые поступления остаются допустимы, если сегодня новых наблюдений нет.

## Воспроизведение тестов

В изолированной копии, без .env и реальных ключей:

```bash
python deploy/verify_wb_worker_synthetic.py
bash deploy/verify_wb_fbs_pg_isolated.sh
```

Первый сценарий блокирует сетевые соединения и использует временные SQLite.
Второй поднимает отдельный PostgreSQL17 на внутренней Docker-сети; он не
подключается к рабочей БД. Тесты не запускать внутри рабочего app/worker.

Выполнено 25.11.2026: 180/180 offline регрессий (145 WB + 35 сканирование,
сотрудники/смены); 8/8 PostgreSQL17.5 на отдельном временном локальном кластере
Windows, случайный loopback-порт, только синтетические credentials/данные.
10 000 заказов, 10 терминалов, 1000 commits за 2.04с; p95 20.8мс.
Тестовый кластер остановлен и удалён. Docker-вариант PG runner на HOSTKEY
в этом прогоне не запускался. Реальный WB API не вызывался.

## Подготовка образов — не развёртывание

Из чистой изолированной копии этого SHA, без реальных файлов поставок/секретов:

```bash
SHA=$(git rev-parse HEAD)
docker build -t "grit-wms:release-$SHA" .
docker build -f deploy/worker.Dockerfile --build-arg "APP_IMAGE=grit-wms:release-$SHA" -t "grit-wms:worker-$SHA" .
```

Образы на HOSTKEY в рамках этой задачи не собраны; рабочие контейнеры не менялись.

## Выпуск только после отдельного разрешения

1. Сохранить ID текущих app/worker образов и точные параметры запуска обоих
   контейнеров в закрытом release-каталоге. Проверить Compose service/все overlays
   отдельно для worker: существующий `hostkey_release.sh` выпускает **только app**.
   Если worker запущен вне Compose, нельзя заменять его выдуманной командой
   `docker run`: сначала зафиксировать воспроизводимый запуск и обратную команду.
2. Проверить backup именно `grit_migration_trial_20261111`, создать свежий dump,
   проверить checksum/оглавление и подтверждение восстановления вне VPS.
   На момент read-only проверки файл `verified-production-offsite-recovery.txt`
   отсутствовал. Это не доказывает отсутствия копии, но подтверждение не получено.
   Не создавать waiver/поддельный receipt и не обходить release guard.
3. После разрешения, в окне работ: выпускать только worker и app, сохраняя
   сеть, секреты, tmpfs, пользователя и все overlays. Для Compose использовать
   последний overlay с образами кандидата и `up -d --no-deps --no-build`
   только для подтверждённых имён двух сервисов. Не запускать две копии worker.
   Сначала worker (создаёт аддитивную таблицу), затем app. Никаких down/volume rm.
4. Контроль: worker health именно `ok`, успешные new/status, отсутствие повторных
   401/403/429, свежесть ВСЕЙ confirm-когорты; app startup/manager-login/login.
   Проверить аналитику чтением, не тестовыми операциями реального склада.
5. При провале вернуть **оба сохранённых image ID** в исходном контексте
   запуска, повторить проверки. БД не восстанавливать поверх текущей: новая
   таблица аддитивна, прежний код её игнорирует; новые складские события сохраняются.
   Автоматический rollback существующего скрипта покрывает только app, не worker.
   Совместный автоматический откат не заявлен проверенным.

Готовность к production переключению: НЕТ до подтверждения восстановления,
проверки образов/точного worker-контекста и явного разрешения владельца.
