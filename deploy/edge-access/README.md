# ONIX WMS · дополнительный HTTPS-вход для склада (тестовый стенд)

## Зачем

30.10.2026 телефон сотрудника открывает ONIX через VPN, а без VPN возникают ошибки. Рабочий ONIX — `https://onix-wms-frankfurt.onrender.com` (Render Frankfurt); PostgreSQL остаётся на Render. **Этот стенд не переносит БД, не меняет рабочий деплой, не меняет авторизацию и не требует секретов ONIX на дополнительном сервере.**

Технически это **один выделенный HTTPS reverse proxy**, а не общий публичный прокси. Сотрудники смогут обращаться к новому домену, а посредник будет получать данные с единственного upstream ONIX на Render.

**Важно:** факт работы с VPN сам по себе не доказывает блокировку Render для всех операторов. Сначала сравни два телефона в одной Wi-Fi-сети, затем диагностику DNS/TCP/HTTPS. Для новой входной точки **необходимо проверить фактическую доступность из склада без VPN**, это нельзя доказать тестом из GitHub Actions.

## Ограничения перед началом

1. Нужен доступный с российских складских сетей VM/VPS с публичным IPv4 и 80/443 TCP, например Compute Cloud в уже используемом Yandex Cloud, если соответствующий ресурс доступен. VM/тариф и стоимость утверждаются владельцем; **этот PR ничего платного не создаёт**.
2. Нужен домен, которым управляет владелец. Укажи A-запись для выбранного поддомена на публичный IPv4 VM. CNAME на `onrender.com` сам по себе **не исправляет** блокировку IP/маршрута.
3. **До установки проверка на самой VM без VPN:** `curl -4 -Iv --connect-timeout 10 https://onix-wms-frankfurt.onrender.com/api/health`. Если с VM этот адрес недоступен, **стоп**: этот вариант не сработает и нужен другой хост/план переноса. Не переноси БД и не меняй исходный адрес.
4. Доступ с телефона до домена VM должен работать без VPN; проверь как минимум складской Wi-Fi и обычный мобильный оператор.
5. Для работы важны задержки при сканировании и продолжительность загрузки; HTTPS-посредник увеличивает один сетевой переход. Сам Render Free продолжит засыпать. Это временный этап, а не гарантия стабильности ONIX 1.0.

## Установка на отдельной Linux VM (после проверки исходящего соединения)

Установи Docker Engine и Docker Compose plugin по официальной инструкции ОС Linux, настрой firewall: TCP 22 только со своего IP, TCP 80/443 публично. Домен направь A-записью на IP этой VM (проверь DNS).

Скопируй каталог `deploy/edge-access` на сервер, открой его, затем:

```sh
cp .env.example .env
# Отредактируй .env: ONIX_DOMAIN=реальный.твой.домен
docker compose config
docker compose up -d
docker compose ps
```

Caddy автоматически выдаёт HTTPS-сертификат, когда действующий домен указывает на VM и TCP 80/443 доступны. **Не отключать TLS-проверку upstream** и **не публиковать ONIX по HTTP**.

## Обязательная проверка без VPN перед переключением сотрудников

```sh
curl -fsSI https://ИМЯ_ДОМЕНА/__edge/health
curl -fsS -o /dev/null -w '%{http_code} %{time_total}\n' https://ИМЯ_ДОМЕНА/api/health
curl -fsS -o /dev/null -w '%{http_code} %{time_total}\n' https://ИМЯ_ДОМЕНА/login
```

Проверить на **реальном смартфоне в складском Wi-Fi без VPN**, не только с VM: открытие `/login`, авторизация по тестовому бейджу, переходы `/fbs`, `/replenishment`, `/` (приёмка), отсканировать тестовый код, проверить защиту от повторного скана, выход по QR старшего и невозможность работы после выхода. Сверить, что под старым и новым доменом **одна база**, но браузерные cookie разные (первый вход на новом домене потребуется заново). Не допускать одновременной работы сотрудника под разными доменами, пока задача #44 о глобальном отзыве сессий не закрыта.

После пилота 4 сканера + 3 менеджера: убедиться, что значения P95 задержек, ошибки и контроли соответствуют эксплуатации. **Не отключать** основной onrender.com адрес до подтверждения на складе и теста отката.

## Откат

Если новый домен даёт сбои, прекратить работу через него и вернуться к исходной ссылке `https://onix-wms-frankfurt.onrender.com` на уже проверенных устройствах/сетях. Данные БД не мигрировали, поэтому не требуется обратная синхронизация. Прокси отключается `docker compose down` (сертификаты в сохранённом томе), DNS можно оставить или убрать позже.

## Безопасность

- Не логировать URL с персональными данными и авторизационные заголовки; в этом Caddyfile нет access-log и нет кэша.
- Не хранить `MOYSKLAD_TOKEN`, `DATABASE_URL` или Flask `SECRET_KEY` на edge VM.
- Весь трафик между браузером, edge и Render проходит по HTTPS с проверкой сертификата.
- Прокси принимает полный HTTP-запрос и может видеть cookie/данные складской операции, поэтому VM должна быть под контролем владельца. Не использовать неизвестные публичные прокси.
- На уровне Render `X-Forwarded-For` и лимиты по IP нужно перепроверить при тесте.
- HTTPS-сертификат, обновление VM, доступ SSH и секреты управления VM остаются зоной ответственности владельца.
