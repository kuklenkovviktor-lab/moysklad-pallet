# PR210 — завершение синтетического контура /fbs → QR → USB Xprinter

## Реализованный путь

1. Работник в уже существующем /fbs и с действующей GRIT-сессией
   сканирует подписанный `GRIT-PRINTER:` QR.
2. Сервер под сессией/CSRF проверяет актуальную смену, активную сборку,
   каталог, штрихкоды, ячейки, линии и исходные синтетические стикеры.
   Выбранные задания попадают в изолированную PG17, повторная очередь
   идемпотентна.
3. Только при явно включённом флаге `GRIT_PR210_AUTO_USB_SYNTHETIC=YES_EXPLICIT`
   и установленном **одном** `GRIT_PR210_USB_PRINTER_ID` сервер создаёт
   до 16 аудитируемых автоматических разрешений `AUTO_USB_APPROVAL`.
   Другие принтеры не могут печатать на этом Xprinter.
4. Оператор один раз запускает `Run-GritUsbTest.ps1 -Mode Auto`
   на Windows. USB-агент, пока режим активен, автоматически опрашивает
   защищённый SSH loopback, забирает только PR210 auto-билеты
   для привязанного принтера, печатает фиксированный синтетический QR
   58×40 через ONIX-TEST-XP460B. Никаких дополнительных действий сборщика.
5. Сервис журналирует `SENDING → SUBMITTED/UNKNOWN`. Повторная
   отправка неопределённого билета запрещена. Spool ACK не равен
   физическому подтверждению.

### Блокирующие границы

- **Только синтетические товары, тестовые PG17 и этикетки `NOT WB`.**
  Production app.py/реальные WB API/база не затронуты.
- Автоматический агент `-Mode Auto` работает **до 16 этикеток** или
  **5 минут**, досрочно завершает через 12 секунд простоя после печати;
  это тестовый ограниченный запуск, а не постоянная Windows-служба.
- Автоматически не печатает реальные WB-стикеры. Реальная
  production-ready интеграция ещё не реализована.
- Несколько печатающих компьютеров и распределение разных USB-принтеров
  не входят в PR210.
- После физического smoke требуется сверить бумагу и QR реальным сканером,
  не повторять `Print` / `Auto` для неопределённых билетов.

## HOSTKEY: сначала выполнить тесты

```bash
DIR=$(mktemp -d /tmp/grit-pr210-XXXXXX)
git clone -q --depth 1 \
  --branch feature/pr210-auto-usb-synthetic-from-fbs \
  https://github.com/kuklenkovviktor-lab/moysklad-pallet.git "$DIR"
chmod 755 "$DIR"
bash "$DIR/deploy/verify_pr210_auto_usb_synthetic.sh" "$DIR"
```

Последняя строка при успехе:
`PR210 AUTO USB SERVER + WINDOWS FAKE-SPOOLER ISOLATED PASS`.

## Только после PASS, для явно разрешённого физического теста

При условии, что **старый PR208 изолированный демо на порту 18769
запущен**, PG17 изолирована, а в ней уже есть ровно один
подтверждённый спулером физический билет, запустить в том же
HOSTKEY-сеансе:

```bash
python3 "$DIR/deploy/arm_pr210_auto_demo.py"
```

Скрипт проверяет старый тестовый app/DB/net, предыдущий
`SUBMITTED_TO_WINDOWS` билет, связывает его единственный printer_id
с ONIX-TEST-XP460B, сохраняет текущие токен и PostgreSQL, заменяет
только demo-app с rollback при ошибке, не касается production.

В Windows PowerShell из **обновлённого checkout PR210**, после проверки
`-Mode Check` и установки тестового рулона:

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
.\deploy\Run-GritUsbTest.ps1 -Mode Auto
```

Тестовый сотрудник в **существующем** `/fbs` демо сканирует
QR именно того связанного принтера, пока `Auto` запущен.
В результате агент выведет `AUTO USB SYNTHETIC SUBMITTED`.
Проверить этикетку и фактический считываемый `GRIT-DEMO-...`.
Прежняя тестовая печать `GRIT-DEMO-...` не является кодом
`GRIT-PRINTER:...` и НЕ должна использоваться как QR принтера.

**Не путать техническую синтетику и готовность GRIT к работе на складе.**
