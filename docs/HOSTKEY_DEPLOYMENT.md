# GRIT WMS: изолированный запуск на HOSTKEY

Это конфигурация **тестового запуска**, а не команда миграции production. Она не
обращается к Render, не импортирует рабочие данные, не меняет DNS и не выполняет
SSH-деплой. Домен `gritwms.space` и VPS `141.105.66.249` указаны только как будущая
целевая инфраструктура. До отдельного разрешения не подключайте рабочие токены
и базу Render и не публикуйте тестовую систему в Интернет.

## Архитектура и границы

- Python 3.12 / Flask / Gunicorn, 1 процесс и 4 потока из существующего
  `gunicorn.conf.py`. PDF (PyMuPDF), Excel (openpyxl), QR (Pillow/qrcode), psycopg,
  requests, boto3 установлены из `requirements.txt` без изменения зависимостей.
- `app`: непривилегированный UID 10001, read-only root filesystem, временный
  `/tmp`, без Linux capabilities; слушает только `127.0.0.1:8000` на хосте.
- `db`: PostgreSQL 17, данные в `/opt/grit-data/postgres`, порт 5432 **не публикуется**.
  PostgreSQL находится во внутренней Docker-сети без внешнего маршрута.
- `backup`: отдельный образ с клиентом PostgreSQL 17 и скриптами. Пишет только
  в `/opt/grit-data/backups`, не подключает каталог исходников. UID 0 без
  capabilities нужен для защищённого каталога резервных копий владельца root.
- Сеть `web` позволяет приложению исходящие соединения для будущих интеграций,
  но реальные API-токены в этой конфигурации принудительно пустые. Заданный извне
  `DATABASE_URL` не используется: entrypoint формирует URL только для `db/grit`.
- Секреты создаются отдельно для теста. Секреты не зашиваются в образ и не
  коммитятся. `.env` доступен только владельцу (0600). Администратор Docker/root
  может читать environment контейнеров — это не хранилище от администратора хоста.
- Нет автоматического обновления образов или деплоя из CI. PostgreSQL major
  нельзя менять на существующем каталоге без отдельного upgrade-плана.

Dockerfile использует version tags; для формального production-релиза закрепите
проверенные digest образов и транзитивные зависимости. Сохраните идентификаторы
собранных образов. Совместимость миграции с версией PostgreSQL Render ещё не
проверена: версия базы источника должна быть установлена до переноса.

## Подготовка HOSTKEY (вручную после проверки PR)

Предпосылки: Ubuntu 24.04, Docker Engine и Compose уже установлены. Клонированная
ветка находится в `/opt/grit-wms`. Существующие файлы и каталоги не удалять.
Следующие команды выполнять **на VPS**, не в окружении Render:

```bash
cd /opt/grit-wms
# Сначала убедитесь, что каталоги предназначены для НОВОЙ тестовой установки:
sudo ls -ld /opt/grit-data /opt/grit-data/postgres /opt/grit-data/backups
```

Если каталоги отсутствуют, создайте их. Если существуют и содержат данные —
остановитесь и проверьте их назначение. Не меняйте владельцев существующей базы
вслепую. Для новых каталогов:

```bash
sudo install -d -m 0755 /opt/grit-data
sudo install -d -m 0700 /opt/grit-data/postgres
sudo install -d -m 0700 -o root -g root /opt/grit-data/backups
python3 deploy/init_env.py
```

Генератор не перезаписывает существующую `.env` и не печатает секреты. Резервную
копию `.env` храните в защищённом хранилище отдельно от Git. Для теста можно
изменить GRIT_DATA_ROOT и GRIT_PORT в `.env`, оставив абсолютный путь на локальный
диск. Не используйте общий каталог с рабочей БД. Переменные shell имеют приоритет
над `.env`: перед запуском исключите старые значения секретов и путей из shell.
В файле намеренно нет DATABASE_URL и API-токенов.

```bash
docker compose config --quiet
docker compose build
docker compose up -d --no-build --wait --wait-timeout 180
docker compose ps
docker compose logs --tail=100 app backup
curl --fail http://127.0.0.1:8000/api/startup
```

Не публикуйте полный вывод `docker compose config` или `docker inspect`: там
есть пароли. Для проверки конфигурации используйте `config --quiet`.

Контейнер app считается healthy только если `/api/startup` вернул ready=true
и отдельное подключение к PostgreSQL выполнило SELECT 1. `/api/health` самого
приложения без MOYSKLAD_TOKEN возвращает 503 — это ожидаемо для изолированного
стенда, этот endpoint намеренно не используется в Docker healthcheck.

Доступ с компьютера администратора без открытия порта в Интернет:

```bash
ssh -L 8000:127.0.0.1:8000 root@141.105.66.249
```

Открывайте `http://localhost:8000/login` для проверки HTML. Приложение требует
Secure-cookie: полноценный вход по обычному HTTP через туннель зависит от браузера
и не является проверкой HTTPS-сессий. Для полного входа используйте одобренный
TLS reverse proxy. Пароль тестового руководителя находится в локальной `.env`;
не выводите файл целиком в общие журналы. Реальные ключи Render не нужны.

## Перезапуск, журналы, наблюдение

Все сервисы имеют `restart: unless-stopped`. После перезагрузки VPS Docker должен
быть включён через systemd. При плановом обновлении сначала сделайте backup,
сохраните текущие image IDs и соберите новый образ; затем пересоздайте app.
Не удаляйте bind-каталоги. `docker compose down` удаляет контейнеры и сети,
но оставляет файлы базы и копии на хосте.

Логи идут в stdout/stderr; драйвер `local` ограничивает каждый сервис пятью
файлами по 10 МБ. Healthcheck не перезапускает unhealthy контейнер сам по себе:
restart policy действует при завершении процесса. Нужен мониторинг
`docker compose ps`/health и ошибок backup с уведомлениями оператору; внешняя
система оповещения этим PR не настраивается.

## Резервные копии

Backup запускается сразу после старта PostgreSQL, затем каждые 86400 секунд.
Настройки: BACKUP_INTERVAL_SECONDS (минимум 60), BACKUP_RETENTION_DAYS (минимум 1).
Создаётся consistent custom-format pg_dump, проверяется список архива, и только
после успеха временный файл атомарно переименовывается. Права 0600. Старые
`grit-*.dump` удаляются по mtime только после успешной новой копии.
Ошибка не удаляет предыдущие копии, повторная попытка — через 60 секунд.
Health backup проверяет возраст отметки последнего успеха.

Ручная копия и список файлов:

```bash
docker compose run --rm --no-deps --entrypoint sh backup /scripts/backup-once.sh
sudo ls -lh /opt/grit-data/backups/
```

Копии на том же VPS защищают от ошибки приложения, но не от потери VPS/диска.
До production нужна дополнительная зашифрованная копия во внешнем хранилище,
контроль свободного диска и проверенный доступ к ней. S3-backup в существующем
`storage_backup.py` при PostgreSQL отключён; он не заменяет этот процесс.

## Проверка восстановления без перезаписи базы

Выберите **точное имя** существующего файла из предыдущей команды. Архив
доступен внутри backup-контейнера под `/backups/<имя>`. Например:

```bash
docker compose run --rm --no-deps --entrypoint sh backup \
  /scripts/restore.sh /backups/<имя>.dump restore_check_manual
docker compose exec -T db psql -U grit -d restore_check_manual \
  -c 'SELECT count(*) FROM employees;'
```

`<имя>` — placeholder, замените его. restore.sh разрешает только новую базу
`restore_check_*`; существующая цель приводит к отказу. Нет `--clean`, dropdb
или перезаписи `grit`. Повреждённый архив отклоняется до создания базы;
ошибка восстановления останавливает команду, тестовая база остаётся для анализа.
Сверяйте не только число сотрудников, но и число строк/последние операции
ключевых таблиц и фактические данные. Для повторной проверки используйте новое
имя базы. Удаление проверочных баз выполняется оператором отдельно.

Восстановление **рабочей** базы требует отдельного разрешения: остановить запись,
снять текущую копию, восстановить в новую проверенную базу, сравнить данные,
подготовить переключение DATABASE_URL в отдельной production-конфигурации и
план отката. Этот скрипт намеренно не переключает app на восстановленную базу.

## Автоматические проверки

```bash
python3 -m unittest discover -s tests/deployment -v
# Требуются зависимости приложения в локальной venv:
docker build -t grit-wms:hostkey .
docker build -f deploy/backup.Dockerfile -t grit-wms-backup:hostkey .
docker pull postgres:17-bookworm
python3 deploy/verify_stack.py
```

verify_stack.py создаёт уникальный Compose project, отдельные секреты и новый
каталог в /tmp; не использует вашу `.env` и `/opt/grit-data`. Проверяет структуру
сети/портов, все healthchecks, HTML входа, тестовую запись, dump/restore, отказ
при повторной цели/повреждённом архиве и сохранность после удаления и создания
контейнеров заново. В finally останавливает только свой project; артефакты
оставляет по выведенному пути для диагностики. Удалять их можно вручную после
проверки. Не запускайте этот тест с удалённым Docker context: bind-пути должны
находиться на том же хосте, где работает Docker daemon.

В управляемом облачном окружении с TLS proxy build выполняется с временным CA:
`docker build --secret id=proxy_ca,src=/etc/ssl/certs/ca-certificates.crt ...`.
На обычном VPS этот параметр не нужен. Проверку TLS отключать нельзя.
CI `.github/workflows/hostkey-deployment.yml` проверяет этот же сценарий и ничего
не развёртывает на HOSTKEY.

## Перед будущим production-переносом

1. Устранить или отдельно принять подтверждённые риски приложения: предсказуемые
   бейджи, конкурентная запись количества при приёмке, сброс встроенных
   сотрудников при инициализации и доверие X-Forwarded-For. Этот PR не меняет
   бизнес-логику и не устраняет эти дефекты.
2. Сверить реально развернутый на Render коммит и версию PostgreSQL, необходимые
   расширения, объём, права и способ безопасного экспорта. Рабочие секреты
   переносить защищённым каналом с сохранением ключей подписи.
3. Подготовить TLS для gritwms.space и reverse proxy с доверенными заголовками.
   Пример `deploy/nginx.conf.example` сейчас **не активировать**: домен и DNS
   в рамках этой задачи не переключаются. Конфигурация теста остаётся loopback.
4. Отдельно разрешить окно остановки записи, финальный экспорт/импорт, сверку
   данных, production-настройки интеграций и переключение трафика. Не запускать
   два независимо пишущих экземпляра на разошедшихся базах.
5. Проверить рабочие интеграции и печать только на разрешённых тестовых данных.
   Сохранить Render для отката; после новых операций на VPS простой возврат DNS
   теряет изменения — потребуется перенос новых данных обратно.
