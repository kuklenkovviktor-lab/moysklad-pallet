# Обновление backup на HOSTKEY: Yandex Object Storage и Telegram

Ветка `fix/hostkey-s3-backups`. Команды ниже — для ручного выполнения **после
проверки PR**, не автоматический деплой. Исправления не меняют исходники WMS,
схему/данные приложения, Render и DNS. Тесты используют свои PostgreSQL и S3
эмулятор, без реальных данных или API-токенов.

## Что изменилось

- Compose ждёт healthy app перед первым запуском backup. Дополнительно каждый
  новый dump независимо проверяет таблицы employees, shifts, scans, activities,
  operation_events, receiving_confirmations, fbs_catalog_barcodes и наличие хотя
  бы одного сотрудника. Если схема не готова, ожидание до 180 секунд и отказ
  без нового архива. Прямая ручная команда также защищена этой проверкой.
- Архив pg_dump проверяется через pg_restore --list, включая TABLE DATA основных
  таблиц, и атомарно публикуется. Параллельные ручной и плановый запуски защищены
  файловой блокировкой. Операция не запускает миграции и не инициализирует БД.
- Загрузка S3: HTTPS с проверкой TLS, таймауты и повторы SDK, multipart для больших
  файлов, уникальное имя, SHA-256 в metadata. После загрузки проверяются HEAD и
  **полностью скачанное содержимое** (размер и SHA-256). У multipart ETag не
  используется как контрольная сумма. Успех фиксируется только после сверки.
- `.pending.json` рядом с архивом — устойчивая очередь. При сетевой ошибке файл
  остаётся на диске; повтор через 60 секунд без нового dump каждую минуту.
  Новый локальный dump создаётся по BACKUP_INTERVAL_SECONDS (по умолчанию сутки).
  Ошибка S3 не прекращает создание новых локальных копий по этому расписанию.
- `<архив>.uploaded.json` содержит подтверждение: endpoint, bucket, object key,
  размер, SHA-256, время и version ID (если bucket versioning включён).
  Не содержит секретных ключей. Смена назначения уже ожидающей копии вызывает
  отказ, чтобы не отправить данные незаметно в другой bucket.
- **Ни старые, ни новые архивы не удаляются автоматически.** Старый
  BACKUP_RETENTION_DAYS больше не используется. Удаляется только собственный
  незавершённый временный файл. Контролируйте свободное место и количество
  ожидающих загрузок; политику хранения согласовать отдельно.
- Ошибки отправляются в Telegram (либо HTTPS webhook). Успешная доставка
  проверяется по HTTP и Telegram `ok=true`. Повтор одинакового доставленного
  уведомления — раз в час; неудачная отправка повторяется на следующем цикле.
  Логи и уведомления содержат этап ошибки, без токенов, URL или текста SDK.
- Healthcheck становится ошибочным при неудачном цикле или неподтверждённой
  загрузке. Healthy локального режима не означает, что S3 включён. Для S3
  проверяется соответствие последней подтверждённой копии текущему назначению.
  При BACKUP_ALERT_REQUIRED=1 также требуется настроенный канал уведомлений;
  факт доставки канала отдельно проверяется notify-test.

## Перед обновлением

На HOSTKEY, `/opt/grit-wms`, сначала проверьте текущие файлы и контейнеры:

```bash
cd /opt/grit-wms
git status --short
git rev-parse HEAD
docker compose ps
sudo ls -ld /opt/grit-data/postgres /opt/grit-data/backups
sudo df -h /opt/grit-data
```

Существующие `.env`, базы и архивы сохранить. Не запускайте init_env.py заново,
не меняйте POSTGRES_PASSWORD и ключи приложения. Не используйте `down -v`,
`rm -rf`, `git reset --hard`, пересоздание БД или рекурсивный chown.
Остановите **только** старый backup, чтобы он не продолжал политику удаления:

```bash
docker compose stop backup
git fetch origin
git switch fix/hostkey-s3-backups
```

Если есть изменения tracked-файлов или локальная ветка отличается — сначала
сохраните и разберите их. Не перезаписывайте локальные изменения.
Приложение и PostgreSQL продолжают работать. Новая конфигурация сохраняет
те же Compose project name, bind-пути и учётные данные базы.

## Настройка Yandex Object Storage

Создайте **отдельный тестовый bucket** без публичного доступа и сервисный аккаунт
с доступом только к нему/нужному префиксу. Не используйте bucket/ключи Render.
Для этого механизма нужны PutObject, HeadObject/GetObject и операции multipart;
DeleteObject не нужен. Ограничьте права политикой bucket. Рекомендуется включить
versioning и серверное шифрование; Object Lock/сроки хранения согласовать отдельно.
Приложение не создаёт bucket, не меняет его ACL/lifecycle и не удаляет объекты.

В существующую `.env` **добавьте или измените только эти несекретные строки**:

```dotenv
BACKUP_S3_ENABLED=1
BACKUP_S3_ENDPOINT=https://storage.yandexcloud.net
BACKUP_S3_BUCKET=<имя-отдельного-тестового-бакета>
BACKUP_S3_REGION=ru-central1
BACKUP_S3_PREFIX=grit-wms/hostkey-test
BACKUP_S3_SSE=aws:kms
BACKUP_S3_KMS_KEY_ID=<идентификатор-отдельного-тестового-KMS-ключа>
BACKUP_ALERT_REQUIRED=1
```

Bucket placeholder заменить реальным тестовым именем. Это не API-токен WMS.
Для Yandex используйте отдельный KMS-ключ и SSE-KMS (`aws:kms`), предоставьте
сервисному аккаунту права шифрования/расшифрования только этим ключом.
BACKUP_S3_KMS_KEY_ID — идентификатор ресурса, не материал ключа. Режим `AES256`
оставлен для S3-провайдеров, поддерживающих SSE-S3; не используйте его как
автоматическую замену SSE-KMS в Yandex. Пустое BACKUP_S3_SSE означает явное
решение использовать настройки шифрования бакета; проверяйте их отдельно. Полное
скачивание для проверки означает дополнительный трафик: учтите стоимость
Object Storage и объём БД. Versioning бакета рекомендуется для защиты старых копий.

Создайте пустой защищённый шаблон, затем внесите ключи в редакторе на сервере:

```bash
python3 deploy/init_backup_env.py
chmod 600 .env.backup
nano .env.backup
```

Если файл уже существует, генератор откажется его перезаписывать — редактируйте
существующий. Заполните BACKUP_S3_ACCESS_KEY_ID и BACKUP_S3_SECRET_ACCESS_KEY.
Файл исключён из Git и Docker build context. В `.env.backup` разрешены только
поля сгенерированного шаблона; не добавляйте туда PGPASSWORD/PGDATABASE/PGHOST.
При смене секретов контейнер backup нужно пересоздать; app их не получает.
Не присылайте файл/ключи в чат и не печатайте `docker compose config` или полный
inspect: там секреты. Используйте `docker compose config --quiet`.

## Telegram

Создайте отдельного тестового бота и чат, разрешите боту отправку сообщений.
В `.env.backup` задайте BACKUP_ALERT_TELEGRAM_TOKEN и
BACKUP_ALERT_TELEGRAM_CHAT_ID. BACKUP_ALERT_WEBHOOK_URL оставьте пустым: при
заполненном webhook он имеет приоритет. Токен не указывайте в аргументах команд.
Ни один тест CI не обращается к Telegram с рабочими токенами.

## Сборка и запуск исправленного backup

```bash
docker compose config --quiet
docker compose build backup
# Убедитесь, что app/db уже Healthy:
docker compose ps
# Пересоздаётся только backup; app/db не трогаем:
docker compose up -d --no-deps --force-recreate backup
docker compose logs --tail=80 backup
docker compose ps
```

Первый новый запуск создаёт полную проверенную копию после проверки схемы.
Прежние архивы без новых sidecar-файлов не добавляются в S3 автоматически:
среди них могут быть старые пустые копии. Новые локальные копии, сделанные этой
версией до включения S3, будут загружены после его включения.

Проверьте Telegram отдельной командой (она намеренно отправляет тестовое сообщение):

```bash
docker compose run --rm --no-deps --entrypoint python3 backup \
  /scripts/backup_worker.py notify-test
```

Код завершения 0 означает успешную доставку; иначе разберите настройки/сеть и
права бота. Дождитесь завершения планового цикла перед ручным backup:

```bash
docker compose run --rm --no-deps --entrypoint sh backup /scripts/backup-once.sh
docker compose exec -T backup sh /scripts/backup-health.sh
sudo ls -lh /opt/grit-data/backups/
```

Если вывод `Backup already running`, код 2: повторять одновременно не нужно.
Проверьте в консоли Yandex, что существует новый объект с ожидаемыми размером,
SHA-256 metadata и SSE. Сохраните `.uploaded.json` в защищённом внешнем месте
для независимой проверки при восстановлении. Нельзя считать внешнее хранение
готовым только по healthy app/db или по наличию локального dump.

При необходимости контролируемой проверки отказа используйте **отдельный**
Compose test-project/эмулятор, а не блокировку рабочих сетей на HOSTKEY.
Для реальной отказоустойчивости нужна ещё внешняя проверка свежести объектов
и уведомление при выключении самого VPS: остановленный сервер не отправит
Telegram. Эта задача реализует уведомления работающего backup-процесса.

## Восстановление скачанного S3-архива без изменения рабочей БД

Из подтверждения возьмите object key и SHA-256, а для нового локального файла —
имя, которого ещё нет в `/opt/grit-data/backups`. Подставьте значения вместо
placeholders, не вставляйте туда секреты:

```bash
docker compose run --rm --no-deps --entrypoint python3 backup \
  /scripts/fetch_s3.py '<object-key>' 'verified-s3-copy.dump' '<sha256>'
docker compose run --rm --no-deps --entrypoint sh backup \
  /scripts/restore.sh /backups/verified-s3-copy.dump restore_check_s3_manual
docker compose exec -T db psql -U grit -d restore_check_s3_manual \
  -c 'SELECT count(*) FROM employees;'
```

fetch_s3 проверяет размер/SHA-256 и не заменяет существующий файл; restore.sh
создаёт только новую базу `restore_check_*`. Для восстановления без локального
подтверждения optional SHA-256 можно опустить: тогда источником ожидаемой суммы
служит metadata S3 по проверенному TLS. Сверьте количество строк, последние
операции и содержимое нужных таблиц; пять сотрудников сами по себе недостаточны.
Переключение приложения на восстановленные данные требует отдельного разрешения.

## Остановка/откат без удаления данных

При проблемах: `docker compose stop backup`. App и db продолжают работать.
Сохраните логи, текущую ветку, image ID и все архивы/состояния. Не включайте старую
политику pruning автоматически. До устранения ошибки делайте новые ручные
pg_dump в отдельные новые файлы и наблюдайте за диском. Возврат старой версии
backup не требует и не должен сопровождаться откатом данных PostgreSQL.

## Проверки разработчика

```bash
python3 -m unittest discover -s tests/deployment -v
docker build -t grit-wms:hostkey .
docker build -f deploy/backup.Dockerfile -t grit-wms-backup:hostkey .
docker build -f tests/deployment/s3.Dockerfile -t grit-s3-test:local .
python3 deploy/verify_stack.py
python3 deploy/verify_stack.py --s3
```

S3-тест использует HTTPS-эмулятор Moto с одноразовым сертификатом и вымышленными
ключами; проверка TLS включена. Проверяются отказ на пустой схеме, полноценный
pg_dump, S3 upload/HEAD/GET/SHA-256, восстановление и сохранность после restart
и удаления/создания контейнеров. Существующие каталоги HOSTKEY тесты не используют.
Unit-тесты покрывают повреждение содержимого, ошибку загрузки, сохранность
очереди, повторы, смену назначения, Telegram/webhook ошибки и отсутствие секретов
в выводе. Реальная доставка в выбранный bucket/Telegram остаётся ручной приёмкой
после внесения секретов на HOSTKEY.
