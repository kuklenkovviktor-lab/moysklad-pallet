# GRIT WMS: очередь печати по линиям, изолированный этап (26.11.2026)

Основа: issue #192, draft PR #193; новое ТЗ от 26.11.2026 о QR-инициированной печати.

## Решение

Целевая модель: **скан QR в существующей сборке → сервер берёт текущие линии принтера и допустимые локальные WB-заказы → атомарно обновляет очередь → агент забирает печатные задания**. Никакого нового рабочего экрана для сборщика, ручного `Забрать заказ`, ручного скана SKU или завершения заказа для печати.

Этот PR реализует **только offline-синтетический SQLite-контракт очереди**, без интеграции в GRIT. Существующий демо-цикл `RESERVED/COMPLETED` из PR #193 не является очередью печати и не переиспользуется как такой.

Компоненты:
- `line_printer_print_queue.py`: изолированное хранение заданий и неизменяемый журнал действий; уникальная пара `(account_id, order_id, sticker_kind)` закрепляет одно логическое печатное задание за одним принтером.
- `scan()`: получает **уже доверенно отобранные** заказы от вызывающего сервиса, добавляет только новые, сохраняет ранее созданные и возвращает счётчики. Повторный скан не переотправляет ничего на физическую печать.
- `transition()`: `QUEUED → SENDING → SUBMITTED → PRINTED`, отдельные `FAILED`, `UNKNOWN`, `CANCELLED`. `SUBMITTED` означает лишь принятие очередью/спулером, не физическое подтверждение.
- `UNKNOWN`/ `FAILED` не перезапускаются автоматически; необходим отдельный подтверждённый менеджерский разбор.
- `PRINTED` и `CANCELLED` терминальны в прототипе. Повторная печать будет отдельной согласованной операцией с аудитом.
- Входы блокируются без явного `GRIT_SYNTHETIC_PRINT_QUEUE=YES_ISOLATED`; запрещён обычный путь базы данных, кроме `:memory:` и локального файла с префиксом `grit_synthetic_print_`. **Это не изоляция от злонамеренного локального процесса и не production auth**.

## Испытания

Локально в отдельной среде проверено:
```bash
GRIT_SYNTHETIC_PRINT_QUEUE=YES_ISOLATED python -m unittest discover -s tests -p test_line_printer_print_queue.py -v
```
17/17 PASS: повторное сканирование, новые поступления, конкуренция восьми потоков с отдельными SQLite-соединениями, история и idempotency по action_id, сохранение после открытия DB заново, отсутствие авто-повтора при UNKNOWN/FAILED, terminal PRINTED, разделение аккаунтов, проверка фикстур и отказ при выключенном gate.

Тесты выполнены **локально**, не на HOSTKEY; эти 17 PASS **не являются** тестированием настоящей PostgreSQL, физической печати, Flask/WMS middleware или WB API.

## Что ещё обязательно до production

1. Перенести контракт в транзакционный PostgreSQL 17 с необходимыми уникальными ключами и конкурентными тестами; решить проблему многократной печати с отдельной управляемой записью разрешённого reprint.
2. Привязать QR к серверному реестру из PR #193. Линии получать **только из текущего реестра**, не из QR и не из HTTP JSON. При изменении линий QR сохраняется, при ротации токена аннулируется.
3. В существующей сборке GRIT обрабатывать QR после реального `QR ВХОД → бейдж`. Защита смены и права доступа на каждом запросе. Серверные допуски вычислять внутри транзакции, не принимать `authorized=True` и `EligibleOrder` от недоверенного клиента.
4. Применять `line_printer_routing.py` к **актуальным** `wb_fbs_orders`, статусам confirm/pending, очереди, исходным WB-стикерам, SKU и подтверждённым активным ячейкам. Конфликт линий — в исключения; без угадывания.
5. Вызов печатного агента с явным журналированием delivery attempt, lease, восстановлением после сбоя и безопасной блокировкой UNKNOWN. USB/spooler ACK **никогда** не равен доказанной физической печати.
6. Добавить менеджерский мониторинг очереди, отдельный безопасный ручной reprint, контролируемую отмену, реальные интеграционные и нагрузочные тесты.
7. Провести независимую проверку в изолированной среде, без живой БД и склада работодателя. Функция должна оставаться OFF по умолчанию; релиз только после отдельного решения.

## Известные ограничения текущего кода

- SQLite-прототип не обеспечивает гарантий PostgreSQL и не должен включаться в production.
- Параметр `authorized` является контрактной заглушкой: нельзя подключать этот класс к открытым HTTP маршрутам.
- Физическая доставка, получение стикеров, контроль застрявшего SENDING/SUBMITTED, повторная печать и актуальность WB между постановкой и отправкой пока **не реализованы**.
- `PHYSICAL_VERIFIED` — условное тестовое свидетельство, а не аппаратно проверяемый факт.
- Нет изменений существующих экранов, таблиц и миграций; никаких реальных заказов или печатных команд.
