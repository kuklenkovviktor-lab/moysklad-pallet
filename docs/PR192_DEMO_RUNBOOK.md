# GRIT PR #193: изолированное браузерное демо на HOSTKEY

**Статус:** подготовлено в GitHub, запуск на HOSTKEY ещё не подтверждён.

## Назначение

Только синтетическая демонстрация маршрутизации заказов по QR принтера.
В production-приложение `app.py` маршруты не добавляются. Файл
`line_printer_demo_app.py` создаёт отдельный Flask-сервис с привычным
тёмным стилем GRIT. Настоящие функции `wms.get_session_employee()`
и `wms.manager_access()` используются через уже проверенный адаптер
`line_printer_wms_auth_adapter.py`, но **авторизация демо-бейджем
синтетическая**; настоящую работу с QR входа/выхода складских ТСД
этот стенд не подтверждает.

Тестовая БД PostgreSQL 17 создаётся под именем
`grit_pr192_synthetic_*`, без внешних томов, на RAM tmpfs.
Учетные записи/смены WMS лежат во второй, временной SQLite
внутри тестового контейнера. Ни один производственный секрет или токен
WB/MойСклад не используется.

Функции:
- Руководитель: создание принтера, изменение названия и линий,
  включение/выключение, ротация QR, скачивание HTML-этикетки 58×40 мм,
  освобождение с причиной, просмотр состояний и журнала.
- Сотрудник: вход через специально созданный демо-бейдж; ввод/скан QR,
  список подходящих синтетических заказов, атомарное закрепление, ввод
  синтетического ШК товара, закрытие заказа при наличии скана.
- Статусы: FREE/RESERVED/COMPLETED/RELEASED, аудит изменений.
- Режим: **без реальной печати WB, без WB API, без использования данных
  склада работодателя и без какого-либо изменения production**.

## Запуск (SSH на HOSTKEY)

На сервере, где доступен Docker и уже есть образ
`grit-wms:release-1cdc36f60f549ba5a86f0ded0d728f2ae368eed4`:

```bash
set -Eeuo pipefail
DIR=$(mktemp -d /tmp/grit-pr193-demo-code-XXXXXX)
git clone -q --depth 1 \
  --branch feature/pr192-line-printer-router \
  https://github.com/kuklenkovviktor-lab/moysklad-pallet.git "$DIR"
chmod 755 "$DIR"
bash "$DIR/deploy/run_line_printer_demo.sh" "$DIR"
```

Скрипт сначала проверяет синтаксис Python, затем запускает **свои**
Docker-сеть, контейнер PostgreSQL и веб-контейнер и вызывает
`deploy/smoke_line_printer_demo.py` по HTTP через
`http://127.0.0.1:18765`. При ошибке запуска собственные
ресурсы удаляются, production не трогается. При успехе сообщает
`PR192 DEMO HTTP SMOKE PASS` и `DEMO START PASS`.

Демо слушает **только localhost**. Для браузера на компьютере:

```bash
ssh -L 18765:127.0.0.1:18765 root@141.105.66.249
```

Затем открыть `http://127.0.0.1:18765/demo`.
Пароль руководителя генерируется при запуске и показывается один раз;
бейдж сотрудника: `DEMO-BADGE-1`. QR генерируется при создании
принтера и сохраняется только в выдаваемой HTML-этикетке.

## Ручной сценарий

1. Войти руководителем по паролю демо, создать принтер А-Б; скачать QR
   58×40 и выбрать бумажную печать через браузер при необходимости.
2. Не закрывая страницу, войти демо-бейджем сотрудника.
3. Считать QR (или уже заполненный код) и получить SYNTH-1001/SYNTH-1002.
   Заказ SYNTH-1003 относится к В, принтер А-Б не должен его выдавать.
4. Зарезервировать подходящий заказ, сверить SYNTH-SKU-*, подтвердить
   сканирование и завершить. Проверить отсутствие повторной выдачи.
5. Для другой заявки войти руководителем, явно освободить её
   с причиной и посмотреть журнал событий.
6. Проверить выключение принтера и перевыпуск QR: старый QR обязан
   перестать действовать.

**Встроенный smoke-тест** уже использует SYNTH-1003 для завершения и
оставляет SYNTH-1001 в состоянии RELEASED. Если нужны исходно пустые
заказы, перезапустить одноразовый стенд.

## Остановка

```bash
bash "$DIR/deploy/stop_line_printer_demo.sh"
```

Либо запустить скрипт остановки из любого клона нужной ветки.
Состояние Docker-контейнеров записано только в
`/tmp/grit-pr192-demo.state`. Команда не обращается к живому Compose.

## Что этот этап не доказывает

- Готовность production-версии, промышленную печать/очередь WB,
  драйверы и подключение USB Xprinter.
- Достоверность каталога и реальных ячеек склада.
- Сквозную работу настоящего процесса QR ВХОД → бейдж → QR ВЫХОД,
  поскольку демонстрационный логин синтетический.
- Возможность полного переноса тестовой схемы lifecycle в живую
  production БД без отдельного миграционного и security review.
- Сетевую доступность на HOSTKEY до фактического запуска и HTTP smoke.

PR #193 сохранять **черновым** до независимого review и подтверждения
всех стадий стенда на HOSTKEY.


## Исправление запуска после `curl: (7)` (25.11.2026)

Первоначальный запуск на HOSTKEY подтвердил `PR192 PYTHON SYNTAX PASS`, но порт `127.0.0.1:18765` был недоступен. При этом встроенный healthcheck производственного образа вызывал в демо `GET /api/startup`, который закономерно отвечал 404: у демо нет такого маршрута. **Это не маркер готовности демо**.

В ветке исправлено: веб-контейнер и одноразовая PG17 находятся в отдельной Docker **bridge** сети, а порт публикуется исключительно на loopback `127.0.0.1`. `--internal` убран, поскольку он мог блокировать путь от хоста к опубликованному порту. Встроенный production healthcheck для демо отключён (`--no-healthcheck`), готовность проверяется по собственному `GET /health`. При падении контейнера печатаются статус и последние 100 строк логов без 60 повторяющихся `curl`.

**Это предположительная причина сбоя до повторного запуска, не подтверждённая корневая диагностика.** Отдельная сеть допускает исходящее соединение из контейнера, но не подключена к production; ни одного рабочего токена или секрета в демо нет. PostgreSQL в tmpfs, локальный порт без внешнего доступа.

Повторный запуск выполняется из **нового** клона ветки. Если он снова упадёт, диагностический блок в конце показывает конкретную ошибку. HTTP smoke и настоящая работа браузерного интерфейса пока ещё не подтверждены.
