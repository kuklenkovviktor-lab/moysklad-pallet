# PR209 — QR принтера внутри существующего сканера GRIT /fbs

**Только синтетическая интеграция.** Без новых страниц/меню/логинов
сотрудника. Нельзя мержить или деплоить в production до появления
проверенного производственного маршрутизатора и операционного print agent.

## Поведение

Сотрудник уже вошёл по бейджу в штатную GRIT и находится на `/fbs`.
Тот же HID/кольцо/камера вызывает исходный `handleScan(code)`.
QR вида `GRIT-PRINTER:...` обрабатывается **до** сканов товара/WB:
скан не попадает в `/api/fbs/product-info` или `/api/fbs/scan`,
не меняет статистику собранных заказов и не сбрасывает pending товар.

Если уже ожидается WB-стикер для ранее отсканированного товара или
есть неподтверждённый WB-outbox, QR принтера отклоняется с понятной
ошибкой без потери ожидающего товара и без повторной отправки WB-заказа.
Поддерживается AIM-префикс сканера `]Q3` только для QR принтера.
Обычные товар/WB сканы не меняются, а штатные экран и дизайн сохранены.

Синтетический сервер выдаёт CSRF только при живой реальной WMS-сессии,
проверяет QR и линию под блокировками отдельной PG17. Повторный скан
идемпотентен; `QUEUED` не значит `PRINTED`.

## Изолированный браузерный стенд

`line_printer_demo_app.py` по-прежнему требует
`GRIT_SYNTHETIC_PG_TEST=YES_ISOLATED`, отдельную PG17 и Docker
loopback-only `127.0.0.1`. Теперь в нём доступен именно **оригинальный
`/fbs`**, а не новый экран. Для работы этого интерфейса добавлены только
необходимые whitelisted маршруты WMS: `/api/auth/me`,
`/api/shift/current`, `/api/fbs/stats`, `/api/fbs/pending`,
`/api/fbs/activity`. Другие производственные API сборки в демо
не регистрируются. Синтетическая очередь при QR работает через
`/synthetic/pr192/print-queue/...`.

**Примечание:** старые `/demo/worker-qr` экраны в PR208 остаются
предыдущими тестовыми harness, не частью целевого процесса.

## Проверка на HOSTKEY

Только отдельный checkout PR209, **не /opt/grit-data production**:

```bash
DIR=$(mktemp -d /tmp/grit-pr209-XXXXXX)
git clone -q --depth 1 --branch feature/pr209-existing-fbs-printer-qr-synthetic \
  https://github.com/kuklenkovviktor-lab/moysklad-pallet.git "$DIR"
bash "$DIR/deploy/verify_pr209_existing_fbs_qr.sh" "$DIR"
```

Скрипт проверяет Python syntax (AST), девять Node-сценариев штатного сканера,
затем полный disposable PostgreSQL17 скрипт с новым HTTP+WMS /fbs
интеграционным набором. В тестах есть защита от чужого QR, закрытой
смены, неверной авторизации, повторного добавления, повреждения
незавершённой пары и изменения показателей обычной сборки.
Без USB, реальных заказов, печати, production-БД/Compose.

**На момент создания PR тесты нового PG17 набора ещё не выполнялись**
на HOSTKEY. Одни только JS проверки в локальном V8 ранее прошли.

## Что НЕ реализовано

- Production endpoint, который связывает реальную очередь WB, МойСклад,
  безопасную проверку стикеров и живую карту линий с принтерами
- Постоянный Windows agent (сейчас подтверждена только одна
  синтетическая физическая отправка через PR208)
- Управление несколькими физическими принтерами, мониторинг и
  автоотправка без менеджерского подтверждения после QR в
  производственной модели
- Совместный нагрузочный и физический acceptance полного
  `/fbs` → USB → Xprinter контура

Не использовать слово «готово к эксплуатации», пока это не проверено.
