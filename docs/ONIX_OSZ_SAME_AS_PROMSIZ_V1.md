# ONIX WMS 1.0: ОСЗ работает по схеме Промсиза

**Область:** только палетные QR и приёмка; не меняет правила WB FBS и адресные остатки.

## Первый запуск ОСЗ

1. Руководитель открывает `/manager/partners` в основной ONIX и создаёт партнёра с отдельным именем **ОСЗ** и уникальным паролем не короче 12 символов. Не использовать учётную запись Промсиза.
2. Представитель ОСЗ входит в `/partners/login`, видит только свои палеты, загружает Excel.
3. **Формат идентичен Промсизу**: `Артикул | Палет | Ед. в палете | Количество, ед.` либо `Палета | Артикул | Количество`. Один товар и количество на палету; смешанные SKU допустимы в данных, но текущая приёмка `/api/scan` поддерживает только одну строку SKU на палету.
4. ONIX создаёт `ONIX-PAL-<случайный уникальный UUID>` на **каждую физическую палету**. QR печатается на листе А4, отображает артикул, номер палеты, количество. На складе считывается только уникальный ID; данные SKU/qty берутся из базы.
5. Приёмщик работает **через обычный режим палетной приёмки** (выбранный черновик МойСклада), сканирует новый `ONIX-PAL`, проверяет позицию/количество, подтверждает. `receiving_confirmations` и статус палеты предотвращают повторную запись.
6. Поставщик видит `Создана/В обработке/Принята/Требует сверки`; можно скорректировать состав **до** приёмки без изменения QR.

## Переход со старых SSCC

- Новые палеты по согласованной схеме маркировать **только одним рабочим QR ONIX-PAL**. Старые этикетки не менять на уже принятых палетах.
- Для физической палеты, на которой ещё существует старый ОСЗ SSCC, добавлять в Excel **необязательную** колонку `SSCC`: 18 цифр как текст. Нельзя записывать SSCC числовой ячейкой Excel: 18-значное число теряет точность.
- После загрузки этот SSCC связан с новым QR. Старый путь `/api/osz/check`/`accept` блокирует его; доступен только единый `ONIX-PAL`.
- Если старый SSCC уже в `external_pallets` или имеется операция в `receiving_confirmations`, новый QR не создаётся. Нельзя принудительно принять без сверки.
- **Если SSCC не указан**, технически невозможно связать старый и новый код физической палеты. В таком случае нельзя использовать старый сканер ОСЗ для этой же палеты; руководитель должен контролировать смену схемы.
- Ни старые неопределённые операции, ни старые документы не удаляются миграцией.

## Критерии приёмки на складе

- [ ] Войти в отдельный кабинет ОСЗ и проверить отсутствие палет Промсиза.
- [ ] Загрузить тестовый Excel: полная и неполная палета, два разных QR.
- [ ] Распечатать А4, отсканировать сканером реальный QR, убедиться в совпадении SKU и qty.
- [ ] В отдельном **тестовом** черновике МойСклада принять одну палету и сверить количество.
- [ ] Повторно сканировать QR: никакой новой строки/прироста в МойСклад.
- [ ] Если используется старый SSCC, проверить отказ его повторной приёмки; проверить старую уже принятую палету на запрет создания нового QR.
- [ ] Проверить обрыв связи, возврат в интерфейс и статус `uncertain` без автоматического повторного списания.
- [ ] Не считать миграцию завершённой без теста на **PostgreSQL** и сценария с реальным Excel ОСЗ. Тесты SQLite и mock API не заменяют этого.

## Изменения

Все поставщики работают через один `partner_pallets.py`, существующие отдельные аккаунты и один маршрут `/api/scan`; нет нового независимого модуля ОСЗ. Добавленная таблица `partner_pallet_legacy_sscc` сохраняет соответствие старого SSCC и нового QR, не меняя существующие коды Промсиза.
