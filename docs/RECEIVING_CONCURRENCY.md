# Сериализация записи документа приёмки

Ветка fix/receiving-document-lock. Предыдущая защита operation_id предотвращала
повтор одной операции, но не гонку двух разных физических палет: оба запроса
читали количество 10 и записывали 15 вместо итоговых 20. Уникальность operation_id
этого не исправляет, поскольку обе операции имеют собственные корректные UUID.

Добавлен общий per-receipt lock вокруг полного get → increment → write и вокруг
проверки/сводки/проведения документа. В PostgreSQL это transaction advisory lock
на отдельном соединении: работает между потоками и процессами одной БД, снимается
при rollback/разрыве соединения. Не добавляет/не удаляет бизнес-таблиц. Существующий
журнал operation_id и uncertain/reconcile остаётся прежним.

Разные документы не блокируют друг друга. В SQLite development используются
thread-lock и Unix file lock; Windows Flask поддерживается только в одном
процессе. Для серверного HOSTKEY используется PostgreSQL. При увеличении числа
Gunicorn threads проверить размер PG pool: текущие 4 threads / 5 connections
оставляют соединение для запросов внутри проведения документа.

Ограничение: lock не координирует ручные изменения в МойСклад, другую систему или
вторую WMS на другой PostgreSQL. При миграции всё равно нужен единственный writer
и остановка Render перед разрешением записи HOSTKEY. Lock не делает распределённую
транзакцию с внешним API и не отменяет ручную сверку uncertain-операций.

4 теста на SQLite и PostgreSQL 17 проверяют итог 20 при двух палетах, независимость
разных документов, освобождение после ошибки API и ожидание завершением документа
той же блокировки. Transport МойСклад полностью искусственный: настоящие API
записи не выполнялись.

```
python -m unittest discover -s tests -v
docker build -t grit-wms:receiving-test .
python deploy/verify_receiving_postgres.py
```

Runner использует только новую локальную Docker PostgreSQL в tmpfs, без портов
хоста или внешнего DSN. Включение на production требует review и отдельного
разрешения; рабочие Render/HOSTKEY не изменялись.
