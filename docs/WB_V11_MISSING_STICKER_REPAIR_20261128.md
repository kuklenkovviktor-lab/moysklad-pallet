# WB FBS v1.1: устраняем «СТИКЕР WB НЕ НАЙДЕН»

## Проверенная причина в коде

Старый `/api/fbs/scan` при `WB_FBS_V11_ENABLED=1` проверяет
сначала точное значение 9-символьного QR по `(account_id,barcode)`
в `wb_fbs_stickers`. `UNKNOWN_STICKER` появляется при отсутствии
совпадений. Это **не ошибка Xprinter/PR211**.

Синхронизация уже сохраняла QR для новых заказов и полной загрузки,
но не имела регулярного отдельного восстановления пропущенных стикеров:
заказ мог появиться до доступности QR или API мог не вернуть стикер при
первом обращении. В этом случае статус заказа продолжал обновляться,
а QR мог отсутствовать до полной/ручной синхронизации.

В текущем `main` также обнаружен **конфликт выбора источника**:
при включённом WB v1.1 маршруты проверки товара/стикера выбирают
WB API **до** автоматического PDF-режима. Однако
`pdf_picking_active()` глобально возвращает `True` для любой
активной смены, когда импортирован хотя бы один PDF.
Поэтому слепое повышение приоритета PDF переключило бы всех сотрудников.
Автоматической смены приоритета НЕ делаем. Добавлен явный
**серверный режим для всей установки**:
`WB_FBS_SOURCE_MODE=api` (по умолчанию, поведение v1.1 сохранено)
или `WB_FBS_SOURCE_MODE=pdf` (только после осознанного выбора и
проверенного импорта PDF). В PDF-режиме нет WB API-проверки статуса,
поэтому это отдельная модель доверия, которую владелец должен одобрить.
При неизвестном режиме или отсутствии PDF сборка останавливается.
Одновременно смешивать API и PDF на разных сменах в одной установке
пока нельзя; в дальнейшем для этого понадобится отдельный
однозначный выбор источника на уровне смены.

**Действительная причина именно конкретного скана пользователя**
без чтения используемой DB/конфигурации HOSTKEY неизвестна.
Возможны: QR отсутствует в WB кэше, выбран не тот аккаунт,
QR есть только в импортированном PDF, иной формат/сбой сканера.
Теперь для различения доступен безопасный инструмент руководителя.

## Что изменено

1. `wb_fbs_sync_v11.py`: каждые **300 секунд** в существующем
   выделенном worker выполняется восстановление отсутствующих
   авторитетных WB API QR для уже известных заказов:
   `local_status=pending`, `wb_status IN (confirm,complete)`,
   `wb_fbs_picking_queue` обязательно.
2. По одному запросу максимум **100 заказов**. Сохранённые в DB
   `wb_fbs_sticker_repair_attempts` ограничивают повторные запросы
   и обеспечивают честную очередь старых и новых пропусков.
   Новая таблица аддитивная, не удаляет и не изменяет имеющиеся заказы.
3. Ответ WB проверяется по точному ID запрошенного заказа и строго
   корректному 9-символьному QR, а не по выдуманному Code128.
   При отсутствии ответа заказ остаётся `UNKNOWN_STICKER` и
   НИКОГДА не засчитывается автоматически.
4. Экран руководителя `/manager/wb-fbs-v11`:
   число ожидающих заказов без стикера, последняя попытка ремонта,
   предупреждение о независимом реестре PDF, и поле
   **«Почему стикер не найден?»** с read-only проверкой QR.
5. `POST /api/wb-v11/diagnose-sticker`: только менеджер,
   CSRF обязательный, без сетевых вызовов/записей; результат
   `IN_SELECTED_ACCOUNT`, `DUPLICATE_CURRENT_ACCOUNT`,
   `PDF_REGISTRY_ONLY`, `NOT_A_NINE_CHARACTER_WB_QR` или
   `NOT_IN_WB_API_CACHE`. Не раскрывает записи других аккаунтов.
6. `app.py` (первый ШК товара) и `wms.py` (второй QR)
   используют **единый выбор источника**. По умолчанию v1.1 остаётся
   API-режимом, без дополнительного обращения к PDF-БД на горячем пути.
   Явно выбранный PDF требует активного PDF и проверяет SKU/стикер
   по `pdf_fbs_orders`; неизвестный источник не принимается.
   Подсказки API в PDF-режиме отключены; API-worker отказывается
   запускаться в PDF-режиме. Изменён код повторной проверки при потере
   ответа: API сохраняет 9-символьную идентичность QR, PDF — 11 цифр.
   **Проверки соответствия товара/стикера и аудит не обходятся.**
7. Добавлены независимые offline unit-тесты и реальные
   SQLite-проверки синтетического сканирования: запоздалый QR,
   повторные попытки, отсутствие ответа WB, изоляция аккаунтов,
   неправильный формат, безопасность менеджера.

## Ввод в эксплуатацию только после проверки и разрешения

- Зафиксировать текущий deployed SHA отдельно для веб-приложения
  и для выделенного WB-worker; не считать GitHub `main` доказательством
  текущего deployed кода.
- Сделать резервную копию и проверить восстановление в отдельной DB.
- После синтетических PASS и code review объединить PR с `main`.
- Отдельно обновить приложение **и** выделенный WB-worker на один SHA.
  Если обновить только веб-сервер, 300-секундный repair не заработает.
- Проверить менеджерскую страницу: `missing_stickers`,
  `last_sticker_repair` и разбор тестового QR.
- Для площадок без авторизованного WB API не включать
  автоматическую проверку WB API без источника. Если владелец явно
  разрешает работу по загруженным оригинальным PDF, зафиксировать
  `WB_FBS_V11_ENABLED=1` + `WB_FBS_SOURCE_MODE=pdf` **только в
  разрешённой тестовой установке**. Никакой подмены статусов WB:
  PDF-сборка подтверждает лишь соответствие товара импортированному
  стикеру. В отдельном процессе WB-worker при PDF-режиме не нужен.
- Параметр `WB_FBS_SOURCE_MODE` действует на всю установку; он не
  предназначен для одновременной работы разных смен в двух источниках.
- Откат: вернуться к предыдущему app/worker image, не удалять новую
  таблицу попыток, никаких обратных миграций с удалением данных.

**Никакого автоматического production-деплоя, изменений в базе
работодателя и использования настоящих WB-заказов в тестах.**
