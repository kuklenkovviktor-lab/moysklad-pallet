# FBS: транзакции и восстановление после потери связи

Ветка `fix/fbs-durable-transactions`. Бизнес-поток остаётся: товар → стикер WB;
для пропуска нужен одноразовый QR руководителя. Новая таблица fbs_scan_requests
добавляется штатным init_wms_db; существующие записи не удаляются и не переписываются.

Подтверждённые прежние окна сбоя:

- INSERT scans, удаление fbs_pending_products и событие фиксировались раздельно;
  сбой между ними оставлял одновременно учтённый заказ и ожидающий товар.
- Проверки смены/деятельности/ожидающего товара не защищали последующий INSERT
  от параллельного завершения, смены операции или QR-пропуска.
- Потерянный ответ не имел устойчивого request_id; повтор возвращал ошибку вместо
  подтверждения уже зафиксированного результата.
- Создание смены/деятельности состояло из отдельных commit; параллельный вход
  мог создавать несколько активных смен, а сбой оставлял неполное состояние.
- Конкурентный импорт PDF после предварительной проверки мог молча проигнорировать
  конфликтующий SKU через ON CONFLICT DO NOTHING.
- Ошибка создания обязательного уникального индекса scans.barcode скрывалась.
- Повторная инициализация включала отключённых встроенных сотрудников и сбрасывала
  их ставку/план/имя/роль. Теперь обновляются только производные коды бейджей.

Теперь критические изменения фиксируются вместе с событием. В PostgreSQL
используется блокировка строки смены, в SQLite — BEGIN IMMEDIATE. QR-пропуск,
подтверждение товара, смена деятельности и закрытие смены используют ту же
границу сериализации. Создание смены сериализовано по сотруднику. Уникальный
индекс WB остаётся последней защитой между разными сменами; при невозможности
создать его приложение отказывает в готовности, не исправляя дубли автоматически.

Браузер сохраняет запрос WB в localStorage ДО отправки. При потере ответа,
перезагрузке или восстановлении соединения повторяется тот же request_id.
Сервер возвращает replayed=true без второго скана и без удаления нового pending.
При недоступном localStorage отправка не начинается. При HTTP 5xx/обрыве запрос
сохраняется; окончательный отказ 4xx освобождает только outbox, не серверный товар.
Запрос другой смены не отправляется автоматически: нужна сверка руководителя.

Legacy-клиенты без request_id сохраняют прежний ответ 409 на повтор WB; новая
мобильная страница использует журнал запросов и требует серверный pending даже
без PDF. Сопоставление QR WB и ограничения PDF перепроверяются внутри транзакции.

## Воспроизведение

```
python -m unittest discover -s tests -v
node tests/test_fbs_outbox.cjs
# Изолированный PostgreSQL, без портов хоста и без production DSN:
docker build -t grit-wms:fbs-test .
python deploy/verify_fbs_postgres.py
```

14 новых тестов выполняются и на SQLite, и на PostgreSQL 17: lost ACK/replay,
конкурентные завершения/QR, rollback события, повторное создание смены, импорт PDF,
переключение деятельности, новый Python-процесс с pending, сохранение отключённого
сотрудника и отказ при отсутствии уникальной защиты. Node проверяет браузерный
outbox (потерянный ответ после server commit, перезагрузка, 5xx, 409, ошибка хранилища).
Это программная имитация отказов, не физический тест телефона/сканера.

Перед объединением: отдельно проверить на целевой копии отсутствие исторических
дублей scans.barcode и нескольких активных смен/деятельностей. Производственные
данные не исправлялись. Предсказуемые альтернативные форматы входа по бейджу и
конкурентное увеличение количества в МойСклад остаются отдельными рисками; этот
PR не следует считать полным устранением всех ранее найденных проблем безопасности.
