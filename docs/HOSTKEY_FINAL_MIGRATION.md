# GRIT WMS: окончательный перенос Render → HOSTKEY

Основная инструкция для владельца. Рабочие серверы при подготовке этой инструкции **не опрашивались**. Примеры путей относятся к HOSTKEY; выполнять их только после ревью PR, зелёного CI и отдельного решения владельца о начале переноса. Не вставлять в Bash URL базы, пароли, команды с `export DATABASE_URL=…` и многострочные блоки. Все команды ниже однострочные; данные вводятся в вопросы Python.

## Что переносится и что необходимо собрать заранее

PostgreSQL хранит бизнес-записи, но не всю установку. Реестр ниже основан на исходниках `main`; наличие дополнительных файлов/переменных в конкретном Render должен подтвердить владелец в Dashboard. Автоматически прочитать их без доступа к рабочей среде невозможно.

| Данные | Фактическое хранилище и исходник | Действие |
|---|---|---|
| Сотрудники, активность, роли, ставки, цели, коды бейджей | `employees`, `daily_targets`; `wms.py` | Все строки дампа; сохранить прежний `WMS_BADGE_SECRET`, иначе при старте меняются производные коды |
| Смены, операции, сканы, статистика, история изменений | `shifts`, `activities`, `scans`, `operation_events`, `shift_admin_actions` | Все строки, включая незавершённые смены; статистика также рассчитывается из них |
| Повторные запросы FBS, ожидающий товар, одноразовые пропуска | `fbs_scan_requests`, `fbs_pending_products`, `fbs_skip_tokens`, `pdf_fbs_shift_modes` | Дамп. Не очищать ожидающие товары/ledger/пропуска после восстановления |
| Заказы WB, сопоставления PDF, каталог, диагностика | `wb_orders`, `pdf_fbs_orders`, `fbs_catalog_barcodes`, `fbs_catalog_meta`, `fbs_scan_diagnostics` | Дамп, включая lazy-created таблицы; исходный PDF не сохраняется: в `pdf_fbs_orders` только данные и `source_sha256` |
| Ячейки, привязки SKU, пополнение, палеты | `cell_sku_assignments`, `cell_sku_assignment_events`, `replenishment_tasks`, `replenishment_locations`, `replenishment_task_events`, `external_pallets` | Дамп |
| Приёмка | `receiving_confirmations` (`receiving_idempotency.py`), операции GRIT | Дамп. Статусы `processing`/`uncertain` блокируют приёмку переноса: сначала ручная сверка с МойСклад |
| Документы, остатки, организации, склады МойСклад | Внешнее API МойСклад (`app.py`), локальные идентификаторы/журнал в PostgreSQL | Не копируются из внешней системы. Сохранить доступ к прежнему аккаунту; проверить соответствие выбранных организации/склада и реальные документы, не создавать их повторно |
| Ozon FBO | `ozon_fbo_supplies`, `ozon_fbo_cargo`, `ozon_fbo_items`, `ozon_fbo_import_warnings`, `ozon_fbo_pick_events`, `ozon_fbo_pick_audit` | Дамп |
| Партнёры, хэши паролей, загрузки и палеты | `partner_accounts`, `partner_uploads`, `partner_pallets`, `partner_pallet_lines`, `partner_submission_tokens`, `partner_pallet_changes`; `partner_pallets.py` | Дамп. Исходный Excel читается из BytesIO, в БД сохраняются разобранные строки и имя файла, не байты XLSX |
| HTTP-журнал маркетплейсов | `grit_marketplace_sync_log`; `marketplace_http_journal.py` использует общий `wms.db_connect` | Дамп PostgreSQL; это не отдельная SQLite при наличии `DATABASE_URL` |
| Серверные задания печати | `onix_test_print_jobs`; `onix_print_bridge.py` | Дамп. Claimed/submitted задания не перепечатывать автоматически |
| Оригинальные PDF WB, Excel поставщиков, выгруженные этикетки | Файлы операторов; PDF/Excel обрабатываются в памяти, многие этикетки формируются в BytesIO | Отдельно собрать оригиналы, если нужна архивная/юридическая история: восстановить их байт-в-байт из БД нельзя |
| Локальная пилотная печать | Рядом с PDF: `ONIX_WB_*_PREVIEW.png`, `*_REVIEW.json`, маркеры блокировки; `onix_wb_label_pilot.py` | Сохранить вместе с исходными PDF, не удалять маркеры уже выполненной печати. Windows spooler/драйверы/настройки принтера остаются на ПК |
| Браузеры сотрудников | Cookies, localStorage: активный сотрудник/смена, pending outbox FBS, выбранные документы, токен терминала | Не входят в дамп; origin Render ≠ gritwms.space. До остановки дождаться подтверждения всех сканов, сверить pending; на новом домене заново войти и настроить терминал. Не очищать старый браузер до сверки |
| Каталоги и API-кэши в памяти | `PACK_CACHE`, `PRODUCT_BARCODE_CACHE`, `PRODUCT_LIST_CACHE`, bootstrap cache в `app.py` | Не долговечное хранилище; загрузятся заново. Долговечный каталог `fbs_catalog_*` входит в дамп |
| SQLite/старые S3-копии | `WMS_DB_PATH` (по умолчанию `/tmp/wms.db`), `storage_backup.py`, `YC_S3_*` | В PostgreSQL-режиме старый backup SQLite отключён. Существующие SQLite/объекты сохранить как архив, не импортировать параллельно с PostgreSQL. Если Render фактически использует SQLite — остановиться, эта инструкция не подходит |
| Код, картинки, шрифты, vendor JS | Git, точный проверенный commit | Перенести через Git; пользовательские файлы вне Git проверить отдельно |
| Конфигурация и ключи | Render Environment/Secret Files; HOSTKEY `.env`, `.env.backup`, будущий `.env.cutover` | Сохранить вне Git с правами 0600, независимую зашифрованную копию — в хранилище владельца |
| PostgreSQL, существующие архивы, S3 очередь/receipts | `/opt/grit-data/postgres`, `/opt/grit-data/backups` | Не перемещать/не очищать. Миграционные bundles — отдельный каталог `/opt/grit-data/migration` |
| TLS | HOSTKEY `/opt/grit-data/caddy/data`, `/opt/grit-data/caddy/config`; Render сертификат управляется платформой | Существующие каталоги Caddy сохранить. Для нового домена сертификат выпускается Caddy; копировать приватный сертификат Render не требуется |

Инструмент перечисляет **все фактические public-таблицы**, а не только перечисленные имена. Для каждой проверяет все строки SHA-256 (сортированные полные JSON-строки, включая NULL), количество, столбцы/default, ограничения/валидацию и индексы. Проверяет последовательности: параметры, last_value, is_called; identity, представления, пользовательские функции, триггеры, enum, расширения, encoding/locale. Неизвестные схемы с данными, large objects, foreign/materialized tables, RLS и non-libc locale требуют отдельного аудита: инструмент останавливается, не заявляет о полном переносе. Пользовательские роли/ACL/владельцы намеренно не импортируются (`--no-owner --no-acl`); права сотрудников в `employees` и партнёрские хэши переносятся. Если используются отдельные PostgreSQL-роли/SECURITY DEFINER-функции (экспорт блокируется), сначала согласовать их владельцев и привилегии.

## Секреты и настройки — значения не присылать в чат

Обязательны прежние Render `SECRET_KEY`, `WMS_BADGE_SECRET`, `WMS_TERMINAL_SECRET`, `MANAGER_WEB_PASSWORD`. Сохранить также `SUPERVISOR_TERMINAL_VERSION`, `SUPERVISOR_QR_PERIOD`, `FBS_RATE`, `FBS_TARGET`, `WB_STRICT_MATCHING`, `WB_SYNC_DAYS`, индивидуальные `MANAGER_LOGIN_*`, `BOOTSTRAP_CACHE_SECONDS`, если они изменены. Смена домена всё равно требует нового входа; сохранение ключей сохраняет совместимость бейджей и подписанных значений.

Интеграции по фактическому использованию: `MOYSKLAD_TOKEN`, `WB_API_TOKEN`, `ONIX_PRINT_AGENT_TOKEN`; экспериментальный HTTP-модуль — `GRIT_MP_WB_TOKEN`, `GRIT_MP_OZON_CLIENT_ID`, `GRIT_MP_OZON_API_KEY`, `GRIT_MP_YANDEX_API_KEY`, `GRIT_MP_YANDEX_BUSINESS_ID`. `GRIT_MARKETPLACE_LIVE_READ_ENABLED` оставлен 0 до отдельного разрешения. Не включать неиспользуемые интеграции.

HOSTKEY `POSTGRES_PASSWORD` **остаётся прежним**, это пароль локального PostgreSQL, не пароль Render. Не менять его простым редактированием `.env`: существующий кластер от этого пароль не изменит. Не запускать `init_env.py` поверх мигрируемой установки. Render `DATABASE_URL` нужен только скрытому экспорту, в app HOSTKEY не передаётся.

S3: `.env.backup` — `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_ALERT_TELEGRAM_TOKEN`, `BACKUP_ALERT_TELEGRAM_CHAT_ID` (или HTTPS webhook). В `.env` — `BACKUP_S3_ENABLED=1`, endpoint `https://storage.yandexcloud.net`, bucket, `BACKUP_S3_REGION=ru-central1`, отдельный префикс, `BACKUP_S3_SSE=AES256` либо согласованный KMS ID, `BACKUP_ALERT_REQUIRED=1`. Если меняется endpoint/bucket/prefix, сначала завершить старую очередь pending с прежними настройками: worker намеренно блокирует перенос уже привязанной очереди в другое назначение. Старые архивы/sidecar не удалять. Сервисному аккаунту нужны multipart upload/complete/abort, HEAD/GET, при versioning GET конкретной версии; KMS — соответствующее разрешение. Включить versioning/сроки хранения на стороне владельца отдельно; не выдавать право удаления готовых объектов без необходимости. Реальный Yandex и Telegram проверяются владельцем до окна переноса.

HTTPS: `GRIT_ACME_EMAIL`, `GRIT_ADMIN_CIDRS` — публичные IP/CIDR менеджеров и агента печати, не частный адрес телефона за NAT. По умолчанию менеджерские маршруты доступны только loopback. HTTPS-overlay закрывает служебные маршруты и убирает публичный порт приложения. PostgreSQL не имеет опубликованных портов.

## 0. Один раз: получить проверенный код

На HOSTKEY подключиться обычным имеющимся SSH-доступом. Скрипты SSH не настраивают и не используют туннель к Render. В Codex эту часть не выполняли.

`cd /opt/grit-wms`

`git status --short`

Если есть изменения отслеживаемых файлов — остановиться и сохранить их отдельно, не выполнять reset/stash/clean вслепую. `.env*` должны оставаться игнорируемыми файлами. После ревью PR владелец получает **точный commit**, содержащий исправления, и делает:

`git fetch origin main`

`git checkout --detach <ПРОВЕРЕННЫЙ_40_СИМВОЛЬНЫЙ_COMMIT>`

Подставить только SHA из проверенного релиза, не имя непроверенной ветки. Checkout меняет код на диске, не запущенные контейнеры; файлы `.env*` и `/opt/grit-data` не затрагивает. Если Git сообщает о конфликте — остановиться. Обычный `git pull` для этого сценария не нужен.

`python3 deploy/migrate.py build`

Контроль: exit 0, собран `grit-migration:ops` с pg_dump/pg_restore 17. Клиент 17 совместим с источником 16. Никакой локальной установки psycopg/pg_dump не требуется. PostgreSQL TCP не использует HTTP proxy; проверить, что VPS может исходяще соединиться с внешним Render PostgreSQL.

Перед новым экспортом выполнить `python3 deploy/migrate.py check-source`. URL вводится скрыто; дамп/каталог bundle не создаются. Проверяются версии pg_dump/pg_restore/psql, соединение psycopg, read-only snapshot, права чтения/ACCESS SHARE на public-таблицы и последовательности, затем реальное TLS-соединение и импорт snapshot через native psql/libpq того же PostgreSQL, что pg_dump. Это не запуск pg_dump и не гарантия полного экспорта: запись архива, полное чтение/manifest и содержимое остаются отдельными этапами. Разбор новых безопасных кодов и сценарий нулевого partial: [RENDER_EXPORT_DIAGNOSTICS.md](RENDER_EXPORT_DIAGNOSTICS.md). Существующий `.partial` не удалять; при новой попытке выбрать новый каталог.

## 1. Экспорт Render без изменения источника

Сначала можно выполнить репетицию при работающем Render; окончательный экспорт делается **ещё раз после остановки всех источников записи** (этап 10). Последовательности не MVCC: при обнаруженном изменении sequence во время экспорта завершение блокируется. Даже стабильная sequence не доказывает отсутствие других записей — остановка writers обязательна для финального экспорта.

`python3 deploy/migrate.py export`

В вопрос пути указать новый `/opt/grit-data/migration/rehearsal-YYYYMMDD-HHMMSS`. В скрытый вопрос вставить **ровно External Database URL Render**, одной строкой, без кавычек, `ssh`, `export`, приглашения shell и обратных слешей. Пароль должен быть корректно URL-encoded; не исправлять URL вручную догадками. Если скопирован URI с `sslmode=require`, взять URL без этого параметра: инструмент требует `verify-full`, использует системный доверенный CA. Не отключать проверку сертификата.

URL не попадает в историю Bash, аргументы процессов/Docker и сохранённую конфигурацию контейнера; передаётся через stdin. На время pg_dump пароль есть в памяти/окружении дочернего процесса — это доступно администратору ОС, поэтому использовать доверенный VPS и приватные файлы. Скрипт читает источник в REPEATABLE READ READ ONLY, pg_dump использует тот же экспортированный snapshot; источник не изменяется. Manifest может создавать нагрузку сортировкой: запланировать окно. До экспорта/restore проверить свободное место отдельно на файловой системе Docker и `/opt/grit-data`: одновременно нужны исходная `grit`, новые восстановленные БД, дампы и временные сортировки; существующие файлы ради места не удалять. Есть timeout на соединение 10 секунд и pg_dump до часа; при больших БД окно/лимит сначала отдельно согласовать.

Контроль: exit 0, сообщение PASS, каталог содержит `database.dump`, `manifest.json`, `checksums.json`. Dump появляется под финальным именем только после успешного pg_dump, проверки TOC, magic PGDMP, минимального размера и стабильности последовательностей. При ошибке остаётся неполный отдельный каталог/`.partial`; не удалять старые архивы, повторять с **новым** именем. Успехом не является просто наличие файла `.dump`.

## 2. Повторная проверка архива

`python3 deploy/migrate.py verify`

Указать путь bundle из этапа 1. Контроль: exit 0, PASS структуры pg_restore и обеих SHA-256. Не изменять manifest/checksums и не вычислять новые checksum поверх повреждённого dump. Если проверка не прошла — не восстанавливать, источник остаётся рабочим.

## 3. Независимая внешняя копия

Сначала настроить S3/Telegram, сохраняя существующие `.env`/`.env.backup`. Если `.env.backup` отсутствует, `python3 deploy/init_backup_env.py` создаёт новый приватный шаблон без перезаписи; значения внести приватным редактором (например, `nano .env.backup`), несекретные параметры BACKUP_S3_* и BACKUP_ALERT_REQUIRED — через `nano .env`. Все имена перечислены выше; дополнительные пояснения — `docs/HOSTKEY_BACKUP_UPDATE.md`. Не выводить `docker compose config` без перенаправления: он раскрывает секреты. Для копии миграционного bundle нужны актуальный backup image и существующие приватные настройки; этап 4 собирает его. Если текущий backup image ещё без скрипта копирования, безопасно собрать его заранее, без перезапуска сервисов:

`docker compose build backup`

`python3 deploy/migrate.py external-copy`

Указать путь bundle. Скрипт копирует dump + manifest + checksums в уникальный S3 prefix `…/migration/<uuid>/`, SSE, условное завершение multipart `If-None-Match: *` запрещает перезапись. Для каждого объекта выполняются HEAD и полное обратное чтение GET с SHA-256, при versioning проверяется конкретный VersionId. Только после проверки всех файлов появляется `external-copy-<uuid>.json` (0600) с адресами объектов, размерами и checksum. Сохранить receipt и сами checksums дополнительно в независимом защищённом месте владельца. Versioning сохраняет предыдущие версии, Object Lock с согласованной retention защищает версии от удаления; receipt не заменяет такую политику.

Контроль: exit 0, receipt с 3 объектами; владелец проверяет доступ к ним из независимого аккаунта/устройства. Скрипт не создаёт bucket/ключи доступа и не меняет политики. Реальная совместимость Yandex с условным CompleteMultipartUpload **должна быть подтверждена здесь на репетиции**. Если провайдер не поддерживает precondition — остановиться, согласовать другой create-only механизм; не ослаблять защиту молча. При ошибке копирования остаются локальный bundle и уже загруженные объекты; повтор создаёт новый prefix. Копия в другой папке того же VPS не считается внешней.

Для отдельного переноса оригиналов PDF/XLSX и локальных журналов печати на машине, где они действительно находятся, выполнить:

`python3 deploy/migrate.py pack-files`

Вопросами выбрать каталог оригиналов и новый каталог bundle **вне** исходного. Скрипт создаёт приватный `files.tar.gz`, `files-manifest.json` со списком имён/размеров/SHA-256 и `checksums.json`, проверяет каждый файл внутри архива, исходные файлы не меняет. Символические ссылки/специальные файлы блокируются, существующий bundle не перезаписывается. Windows spooler/драйверы этим не переносятся. При работе на Windows использовать Python 3; SSH не нужен для упаковки локальных оригиналов.

`python3 deploy/migrate.py verify-files`

После безопасной доставки этого отдельного bundle на HOSTKEY проверить его заново; затем `python3 deploy/migrate.py external-copy-files` отправит все три файла в независимый S3 prefix с теми же проверками. Обычный `external-copy` копирует только PostgreSQL bundle, не подбирает произвольные файлы/секреты автоматически. Конфигурацию и секреты сохранить отдельно в зашифрованном хранилище владельца; `tar.gz` не является шифрованием. Не публиковать архив с `.env` в GitHub.

## 4. Обновить тестовую HOSTKEY, сохранив кластер

`python3 deploy/migrate.py preflight`

Проверяются локальный Docker socket, приватные файлы, существующий контейнер db, PostgreSQL 17, Compose working_dir/config_files, существующий bind mount и совпадение вычисленного пути хранения. Неизвестный Compose project/overlay, volume вместо bind, другой major или путь дают STOP. Не обходить это созданием нового db. Для нестандартного проекта сначала отдельно согласовать Compose-конфигурацию. Запускать команды от того же root, который управляет текущей установкой.

`python3 deploy/migrate.py update`

Ввести `UPDATE TEST APP`. Скрипт до простоя собирает app/backup/ops, сохраняет приватные конфиги (0600) в новый `/opt/grit-data/migration/update-*`, останавливает **только app и backup**, экспортирует baseline текущей тестовой `grit`, пересоздаёт только app (`--no-deps --no-build`), сверяет все прежние данные/схему (допускается только строго проверенная новая пустая таблица PR93), проверяет неизменность container ID db и конфигов, создаёт резервную копию и пересоздаёт backup. Вызовов up/pull/recreate для db нет. Данные `/postgres`, старые `/backups`, `.env`, `.env.backup` не удаляются и не перезаписываются.

Контроль: exit 0, PASS сохранения. Если ошибка после остановки — не продолжать перенос: сохранить вывод без секретов, `stop` ниже, использовать baseline для новой проверочной БД. Не поднимать старый app автоматически: старые версии могли перезаписывать сотрудников при init. Не делать rollback кластером поверх текущих данных.

## 5. Пробное восстановление — всегда новая БД

`python3 deploy/migrate.py trial`

Указать bundle репетиции и новое имя `restore_check_rehearsal_YYYYMMDD_HHMMSS`. Создание эксклюзивное, `grit`/`postgres`/существующие restore_check запрещены. Восстановление single transaction, `--exit-on-error`, без `--clean`/DROP. Шаблон template0, encoding/locale как в источнике; недоступная locale/extension останавливает этап. Тестовая БД `grit` остаётся как есть. Не использовать один restore_check для двух попыток.

Контроль: exit 0. Автоматически совпали все строки/схема, последовательности/объекты/locale и нулевые счётчики нарушений. При несоответствии новая БД сохраняется для диагностики, источник и `grit` не затрагиваются. Исправлять несовместимость следует на отдельной репетиции, не на исходном Render.

## 6. Ключи и старт восстановленного приложения без интеграций

`python3 deploy/migrate.py prepare-live`

Указать имя restore_check репетиции. Ввести прежние Render signing keys/пароль менеджера скрытым вводом; токены интеграций — тоже скрыто, Enter для неиспользуемых. `.env.cutover` создаётся исключительно новым файлом 0600, `.env`/`.env.backup` сохраняются. Дополнительные изменённые Render настройки из списка выше перенести приватным редактором в `.env.cutover`, не командами shell. Для финального имени позже изменится только `GRIT_DATABASE_NAME`; файл нельзя генерировать заново случайными ключами.

`python3 deploy/migrate.py trial-app`

Указать bundle и восстановленную БД. Запускается обновлённый app на ней с сохранёнными ключами, loopback HTTP, без MOYSKLAD/WB/print/marketplace credentials. App тестовой `grit` на время останавливается, сама БД сохраняется; backup тоже останавливается, чтобы не создавать впечатление защиты неверной базы. Скрипт сверяет данные до и после startup. Неразрешённая миграция/изменение данных → остановка app. Версия PostgreSQL 16 → 17 разрешена, потеря записей — нет.

Контроль: PASS и Healthy, локально `http://127.0.0.1:8000` (если GRIT_PORT иной — прежний порт); /api/health без МойСклад-токена может возвращать 503, готовность проверяется через /api/startup + SELECT1. Публичный служебный endpoint закрыт Caddy намеренно.

## 7. Подготовка HTTPS без преждевременного публичного запуска

До финального cutover проверить DNS A/AAAA, владение доменом, firewall TCP80/443 и UDP443 (необязательный HTTP3), время/NTP, доступ Caddy к ACME. **Эта инструкция DNS не меняет автоматически.** Сохранить старые записи/TTL и решение владельца о переключении. Неверная AAAA может сорвать ACME и мобильный доступ. PostgreSQL5432 не открывать.

Конфигурация готова в `compose.https.yaml`/`deploy/https/Caddyfile`: автоматическое продление, HTTPS redirect, HSTS, no-sniff, frame policy, camera same-origin, внутренние/admin маршруты с ограничениями; менеджерские публичные CIDR указаны в `.env.cutover`. Данные Caddy постоянно хранятся отдельно. Публичный сертификат невозможно проверить в Codex без DNS/ACME и доступа к VPS; тест с частным CA не доказывает выпуск реального сертификата.

Не запускать overlay вручную с базовым `.env`: для production нужен также `compose.restore.yaml`, иначе app снова выберет тестовую `grit`. Для первого запуска пользоваться `start-live` ниже, для остановки — `stop`.

## 8. Интеграции и печать

До остановки Render сверить существующие аккаунты и права токенов, сохранить настройки, **не посылать реальные токены в репетиционный app**. `compose.live.yaml` подключает необходимые токены только на финальном запуске. Старые `YC_S3_*` SQLite restore не включать.

В локальном Windows-агенте печати адрес ранее был жёстко Render. Теперь после переключения выбрать явно:

`python onix_print_agent.py --once --server https://gritwms.space`

Это opt-in диагностическая этикетка на разрешённую тестовую очередь, не массовая печать. Не запускать такой агент одновременно против Render и HOSTKEY. Публичный адрес агента должен входить в GRIT_ADMIN_CIDRS. Реальный принтер/драйвер/физический выход бумаги проверяет владелец, Codex этого не проверял.

## 9. Репетиция складских процессов

На копии, без внешних токенов: вход/роль и прежний бейдж, активная смена и история/статистика, pending товар, PDF WB → сопоставление, повтор/потеря ответа скана, одноразовый QR менеджера, привязка ячеек/пополнение, уникальность палет, партнёрский вход/этикетка, Ozon. Проверить камеру на мобильном HTTPS после допуска; HTTP loopback на ПК не проверяет телефон.

Репетиционные записи изменяют копию: **её нельзя считать финальной и сравнить с исходным dump после ручных операций**. Перед финалом восстановить новый dump в НОВУЮ БД. Сохранить результаты сценариев, не пытаться очистить копию DELETE/DROP.

## 10. Финальное переключение: единственная пишущая сторона

1. Согласовать окно. Закрыть доступ сотрудников к старой WMS, дождаться ACK всех сканов/очередей на телефонах, сверить pending и МойСклад `processing/uncertain`. Сохранить локальные документы/маркеры печати. Не обрывать подтверждение приёмки между внешним API и локальным ledger.
2. **Владелец вручную останавливает/приостанавливает Render web, background workers, cron/других writers и агентов печати**, проверяет завершение процессов/запросов. Auto Deploy=off само по себе не останавливает записи. Maintenance-страница/смена DNS не доказывают остановку writers: старый URL/открытые телефоны продолжают работать. База Render остаётся существующей, без удаления/изменения схемы. Этот организационный шаг не выполняется скриптами и требует отдельного разрешения на рабочую инфраструктуру.
3. Выполнить `export`, `verify`, `external-copy` заново в `/opt/grit-data/migration/final-YYYYMMDD-HHMMSS`, пока все Render writers остановлены. Внешняя копия и receipt обязательны. При ошибке — HOSTKEY не запускать, владелец может вернуть только Render.
4. `trial` в новое имя `restore_check_live_YYYYMMDD_HHMMSS`. Приватным редактором изменить в `.env.cutover` **только** GRIT_DATABASE_NAME на это имя. Старые `grit` и rehearsal DB остаются. `trial-app` с финальным bundle, затем `compare` — только startup, **без создания тестовых бизнес-записей**. Любое несовпадение требует остановки и новой репетиции, не исправления исходного manifest.
5. Только после успешной сверки, подтверждения внешней копии, сохранения файлов/ключей, готовности DNS/ACME и остановки Render:

`python3 deploy/migrate.py start-live`

Указать финальные bundle/БД, вручную подтвердить `RENDER WRITERS STOPPED`. Подтверждение является заявлением владельца, скрипт не может проверить удалённый Render. Скрипт требует совпадающий receipt трёх S3-файлов, ещё раз сверяет БД, требует S3 и обязательные уведомления, проверяет доставку тестового уведомления и принудительно создаёт/загружает свежую копию выбранной финальной БД (недавняя копия тестовой `grit` не подходит), требует успешного backup-health, затем включает live/restore/HTTPS overlays, app, backup, Caddy. db не пересоздаётся, `grit` не меняется. Ошибка запуска останавливает целевые app/backup/Caddy; базы/архивы сохраняются. Уже выполненные внешние операции автоматически не отменяются.

6. Владелец выполняет согласованное изменение DNS/маршрута, если оно необходимо; проверяет HTTPS с обычного телефона через мобильную сеть: валидная цепочка и hostname, login/camera, разрешённый менеджер, служебные URL404, отсутствие открытого5432, Healthy app/db/backup, свежий архив **финальной** БД, успешные S3 receipt и Telegram. `--wait` Caddy означает running, а не гарантированную выдачу сертификата. Не допускать сотрудников до ручной проверки сертификата.
7. Выполнить ограниченный согласованный реальный складской сценарий, сверить его ровно однократную запись в HOSTKEY и нужный документ МойСклад; посмотреть статистику и смену. Render writers остаются остановленными, даже если старый URL доступен. После появления первых новых записей на HOSTKEY возвращать старый Render без обратной сверки/переноса **нельзя**.

Для штатных дальнейших перезапусков сохранять набор файлов `.env` + `.env.cutover` и overlays `compose.yaml`, `compose.ops.yaml`, `compose.restore.yaml`, `compose.live.yaml`, `compose.https.yaml`. Не использовать одиночный `docker compose up`: он выбирает тестовую базу и отключает интеграции. `start-live` специально сверяет исходный bundle; после новых бизнес-записей он уже не является командой ежедневного рестарта. Отдельный эксплуатационный restart следует согласовать с сохранением этого же набора Compose-файлов и выбранной БД.

## Остановка и откат

`python3 deploy/migrate.py stop`

Останавливает только HOSTKEY app/backup/Caddy, не db. До первых HOSTKEY записей и внешних изменений: владелец убеждается, что целевые writers остановлены, возвращает прежний маршрут/Render writers; PostgreSQL Render не изменялась экспортом. Код/конфиги/архивы и все restore_check остаются для анализа. Не копировать файлы живого PostgreSQL вместо pg_dump, не запускать старую и новую WMS одновременно.

После HOSTKEY записей/изменений в МойСклад: остановить обе стороны, сохранить новую HOSTKEY базу, согласовать reconciliation и отдельный обратный перенос. Простой DNS rollback потеряет новые операции. Существующие архивы, тестовые и восстановленные БД не удалять. Команды очистки volumes, пересоздания db и `pg_restore --clean` не входят в сценарий и запрещены.

## Безопасная диагностика

| Ошибка | Проверка владельца без раскрытия секрета | Безопасное действие |
|---|---|---|
| DNS | Верный внешний Render host в Dashboard, DNS на машине экспорта | Исправить источник URL/сеть; новый bundle |
| TCP_OR_FIREWALL | Исходящий TCP к PostgreSQL-порту из URL, Render external access/allowlist | Согласовать правило; не открывать HOSTKEY5432 |
| TLS | Время ОС, системный CA, hostname URL, сертификат Render | Исправить trust/URL, не использовать sslmode=require/insecure |
| AUTHENTICATION | Пользователь/актуальный URL и percent-encoding из Dashboard | Вставить заново скрыто; не печатать URL |
| URL_OR_SCHEMA_OR_ARCHIVE | Одна строка без кавычек/ssh, требуемые таблицы, версия pg_dump, нестандартные схемы | Остановиться и разобрать в приватной сессии; не продолжать с частичным dump |
| SSH disconnect | Подключение к самому VPS, существующий ключ и порт22 | SSH нужен лишь как терминал владельца. Экспорт идёт прямым TLS, туннель не требуется. После разрыва проверить статус; повторный экспорт только в новый каталог |
| Existing destination/database | Выбрано уже использованное имя | Новое имя; ничего не удалять/не перезаписывать |
| Сбой S3/Telegram | Endpoint/region/CA/права/политики, свежий receipt/ошибка health | До исправления не переключать. Не считать локальный dump внешней копией |
| Непонятная ошибка команд | Docker socket, существующий Compose project, приватные права; безопасные диагностические сообщения | STOP; не публиковать полный config/env/traceback с реальными реквизитами |

## Что нельзя подтвердить без доступа владельца

Фактические значения/полноту Render Environment и Secret Files, persistent disk и оригиналы документов; отсутствие неучтённых writers; размер/locale/extensions реальной БД; сетевой/TLS доступ к внешнему Render URL; реальную целостность её записей; установленный commit/project/bind paths HOSTKEY; настройки Yandex/Telegram/KMS, независимое получение копии; DNS/AAAA/firewall/ACME; реальную мобильную камеру/печать и внешние документы МойСклад. Любой такой пункт остаётся проверкой перед cutover. Результаты Codex относятся только к искусственным стендам — см. `docs/FINAL_MIGRATION_TEST_REPORT.md`.
